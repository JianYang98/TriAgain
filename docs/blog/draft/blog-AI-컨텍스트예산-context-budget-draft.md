# 리팩토링을 했는데 프로덕션 코드는 한 줄도 안 바뀌었다

> **TL;DR**: LLM 에이전트와 페어프로그래밍할 때, API 명세 문서 한 개(2,441줄)를 매 작업마다 통째로 읽고 있었다.
> 컨텍스트(토큰)도 유한 리소스다. 런타임을 프로파일링하듯 협업 컨텍스트를 측정·최적화했다.
> 결과: 작업당 문서 로딩 2,441줄 → 460줄(5.3×↓), 엔드포인트 45개 무손실, **프로덕션 코드 0줄 변경.**

사이드 프로젝트 [TriAgain(작심삼일 크루)](https://github.com/JianYang98/TriAgain)를 요즘 AI 에이전트(Claude Code)랑 페어로 짠다.

어느 날 문득, 엔드포인트 **하나** 고치는데 뭔가 매번 느렸다.
새 API를 하나 붙이려는데, 에이전트가 작업을 시작하기 전에 `api-spec.md`를 연다. 매번. 통째로.

그게 2,441줄짜리였다.

---

## 1. 리팩토링을 했는데, 코드는 안 건드렸다

먼저 결론부터. 이 글에서 내가 한 리팩토링은 프로덕션 코드를 **한 줄도** 바꾸지 않았다.
컨트롤러도, 엔티티도, SQL도 그대로다.

바꾼 건 딱 하나 — **AI가 일하는 방식(하네스)**이다.

이게 무슨 소린지 설명하려면, 내가 뭘 놓치고 있었는지부터 얘기해야 한다.

## 2. 이상한 낭비 — 매번 책 전체를 펼치고 있었다

내 프로젝트엔 규칙이 하나 박혀 있다. `CLAUDE.md`에 이렇게 써뒀다.

> Phase A: 관련 문서(biz-logic.md, **api-spec.md**, schema.md 등)를 먼저 읽고 구조를 파악한 뒤 수정할 것

좋은 규칙이다. 문서를 정본으로 삼고, 코드보다 문서를 먼저 고치게 만든다.

근데 부작용이 있었다.
습관(솔로 모드) 엔드포인트 하나를 고치려는데, 에이전트는 `api-spec.md`를 연다.
그 안엔 크루 API도, 인증 업로드도, 알림도, 카카오/애플 로그인도 전부 들어 있다.

메뉴판에서 한 줄 보려고 매번 책 전체를 메모리에 올리는 셈이다.

런타임이었으면 바로 잡았을 냄새다. 근데 이건 런타임이 아니라 "나랑 AI가 협업하는 방식"이라, 그동안 그냥 넘겼던 거다.

## 3. 얼마나 큰데?

측정부터. 감으로 "긴 것 같다"는 최적화의 근거가 못 된다.

```bash
$ wc -l docs/spec/*.md
   2441 api-spec.md      # ← 얘 (분할 전 스냅샷; 지금 이 파일은 38줄 라우터)
    647 biz-logic.md
    525 schema.md
    373 user.md
    ...
```

`api-spec.md` 하나가 **2,441줄 / 약 70KB**. 나머지 spec 문서를 **전부 합친 것보다 크다.**
토큰으로 치면 한 번 읽는 데 대략 **18~20k 토큰**. 엔드포인트 하나 고치자고 매번 이걸 다 태운다.

| 문서 | 라인 | 읽을 때 대략 토큰 |
|------|------|------------------|
| **api-spec.md** | **2,441** | **~20k** |
| biz-logic.md | 647 | ~9k |
| schema.md | 525 | ~4k |
| 나머지 6개 | 100~370 | 소량 |

숫자를 보니 확실해졌다. 최적화할 게 있다면 여기다.

## 4. 근데 사실, 자동으로 읽히는 것도 아니었다

여기서 한 번 멈췄다. "매 세션 자동 로딩되니까 문제다"라고 생각했는데 — 아니었다.

`CLAUDE.md`의 참조 표는 자동 로딩이 아니다. 그냥 "필요하면 여기서 찾아라"는 안내다.
문제는 그 **"필요할 때"가 너무 자주** 온다는 거였다. 엔드포인트 1개 작업, 리뷰 1회, 문서-코드 대조 1회 — 그때마다 전량 로딩.

이걸 정확히 짚는 게 중요했다.
"자동 로딩을 끄자"였으면 헛다리였다. 진짜 비용 경로는 **"단일 작업이 전체 문서를 요구하는 구조"** 그 자체였으니까.

> 런타임에서도 똑같다. "CPU가 높다"가 아니라 "어느 경로가 CPU를 먹나"를 짚어야 튜닝이 산다.

## 5. 그냥 반으로 자르지 않았다

처방은 분할. 근데 **어떤 축으로 자르느냐**가 핵심이었다.

라인 수로 반 자르면? 최악이다. 크루 API가 두 파일에 걸친다.
그래서 **바운디드 컨텍스트**로 잘랐다. 내 프로젝트는 어차피 DDD 헥사고날이라, 도메인 경계가 이미 있다.

```text
docs/spec/api-spec.md          38줄  ← 라우터/인덱스 (개요 + 엔드포인트→파일 표)
docs/spec/api-spec/
├── auth-user.md      547줄  (auth/* + users/me + 프로필 이미지)
├── crew.md           829줄  (crews/* + invite 랜딩)
├── verification.md   322줄  (upload-sessions + verifications + SSE)
├── notification.md   212줄  (fcm-token + notifications/*)
├── habit.md          460줄  (솔로 모드 전체)
└── internal.md        81줄  (internal/* — Lambda 콜백)
```

원래 `api-spec.md` 자리엔 **라우터** 한 장만 남겼다. 개요 + "어느 엔드포인트가 어느 파일에 있는지" 인덱스 표.

이제 습관 작업이면 `habit.md` 460줄만 읽는다.
2,441줄 → 460줄. **5.3배** 줄었다. 인증 작업이면 322줄, 7.6배.

DDD를 코드에서만 쓰라는 법은 없다. 문서 구조에도 같은 경계가 먹힌다.

## 6. 45개, 하나도 안 잃었는지 어떻게 아나

2,400줄을 손으로 옮기면 반드시 뭔가 흘린다.
그래서 옮기는 건 손이 아니라 **라인 범위 슬라이싱**으로 했다. 원본의 20~172줄은 그대로 verification으로, 311~851줄은 그대로 auth-user로. 재입력이 없으니 전사 오류가 없다.

그리고 검증. 콘텐츠가 안 샜다는 건 위 **슬라이싱(verbatim 복사)** 자체가 보장한다 — 재입력이 없으니까. 그 위에 **`### ` 헤더 대조**로 "엔드포인트가 하나도 빠지거나 뒤섞이지 않았나"를 교차 확인했다. 부하테스트에서 `checks_failed`로 서버 건강성을 본 것과 같은 결의 확인이다.

```bash
$ grep -c '^### ' api-spec.original.md      # 원본 엔드포인트 헤더
47
$ cat api-spec/*.md | grep -c '^### '        # 분할본 합계
45
```

47 − 45 = 2. 어? 두 개 사라졌나?

```bash
$ diff <(grep '^### ' 원본 | sort) <(cat api-spec/*.md | grep '^### ' | sort)
< ### Moderation Context
< ### Support Context
```

아, TODO 섹션의 미구현 항목 2개다. 그건 라우터에 남겨뒀다.
**엔드포인트 45개 = 45개. 하나도 안 잃었다.** 숫자로 확인.

## 7. 문서만 바꾸면 끝이 아니다

여기서 두 번째 함정. 문서를 쪼갰으면, 그 문서를 **가리키던 것들**도 다 갱신해야 한다.
`new-api.md` 스킬은 "api-spec.md에 엔드포인트 추가하라"고 지시한다. 이제 그건 틀렸다 — 라우터에 추가하면 안 된다.

근데 "api-spec.md"를 언급하는 곳을 세어보니 하네스 전체에 **수십 군데**였다.
그걸 다 고치면? 그 자체가 리스크다. 하나 놓치면 깨진 참조.

그래서 설계를 하나 넣었다. **라우터가 stale 참조를 흡수하게** 했다.
갱신 못 한 참조가 `api-spec.md`를 열어도, 거기엔 "분할됨 → 이 표에서 도메인 찾아가라"는 인덱스가 있다. 길을 잃지 않는다.

덕분에 실제로 고쳐야 할 지시 라인은 **8곳**으로 줄었다. "엔드포인트를 여기 추가하라"는 문장과 "정본 위치" 포인터만.
나머지 "api-spec.md ↔ 코드 일치" 류 언급 수십 개는 라우터가 라우팅해주니 **손대지 않았다.**

> 마이그레이션에서 구버전 경로를 리다이렉트로 살려두는 것과 같은 발상이다. 한 번에 다 갈아엎지 않는다.

## 8. 대상만 바뀌었다

정리하면 이번에 한 건 이거다.

| 단계 | 부하테스트에서 | 이번에 |
|------|---------------|--------|
| 관측 | 피크 테스트가 FAIL을 찍음 | 엔드포인트 1개에 명세 전량 로딩 |
| 측정 | p95, CPU, HikariCP | `wc -l` = 2,441줄 / ~20k 토큰 |
| 처방 | 락 전략 전환 | 바운디드 컨텍스트 분할 |
| 검증 | `checks_failed` 0% | `### ` 헤더 대조, 45/45 |
| 여파 | 리셋 SQL 정합성 | 라우터가 stale 참조 흡수 |

**관측 → 측정 → 처방 → 검증.** 루프는 똑같다. 대상만 CPU에서 토큰으로 바뀌었을 뿐이다.

우리는 런타임 성능은 당연히 측정한다. 근데 "AI랑 협업하는 방식" 자체는 그냥 감으로 굴리는 경우가 많다.
컨텍스트도 유한 리소스다. 매 요청이 토큰을 먹고, 관련 없는 걸 잔뜩 읽으면 에이전트도 산만해진다.

그러니 프로파일링 대상에 하나 더 넣자.
**내가 AI에게 매번 읽히고 있는 것.** 그게 정말 이 작업에 필요한 만큼인지.

리팩토링은, 프로덕션 코드에만 하는 게 아니다.
