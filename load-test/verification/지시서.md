 # 부하테스트 기록 검증 및 원자재 추출 지시서

  ## 목적
  부하테스트 기록 전체에서 이력서/면접/블로그용 근거 자료를 추출·검증한다.
  문장 작성은 하지 않는다. 검증된 사실과 수치만 정리한다.

  ## 그라운딩 규칙 (최우선, 모든 산출물에 적용)
  - 모든 수치는 실제 기록(k6 출력, 서버 로그, Prometheus, ss/nstat/netstat/tcpdump 출력, 결과서, 회고 문서)에서만 인용한다.
  - 각 수치마다 출처를 명시한다: [회차 식별자, 날짜, 파일 경로 또는 로그 위치]
  - 기록에 없는 값은 추정하지 말고 "기록 없음"으로 표기한다.
  - 기록 간 수치가 충돌하면 둘 다 표기하고 충돌 사실을 명시한다.
  - 회고 문서의 서술과 원본 로그가 다르면 원본 로그를 우선하되, 차이를 반드시 보고한다.

  ## 사전 작업: 회차 인벤토리 (다른 산출물보다 먼저 수행)
  모든 테스트 회차를 식별하고 각 회차에 대해 기록한다:
  - 회차 식별자(파일명/폴더 기준) | 날짜·시각 | 락 전략(비관/낙관/조건부)
  - VU 그리드 (예: 50/100/200/300 또는 20/50/100/200/300/500/700 — 회차마다 다름. 실제 사용된 그리드를 그대로 기록)
  - 설정값: accept-count(기본/256), tcp_max_syn_backlog(설정값/초기화 여부 불명 포함)
  - 네트워크 환경(집/핫스팟/카페/불명)
  - 로그 보유 수준: [k6만 / k6+Prometheus / k6+서버로그 / k6+커널지표(ss·nstat·tcpdump)]
    ※ 서버·커널 로그는 후반 회차부터만 존재함. 초기 회차는 k6 출력만 있을 수 있음.
  - 이 인벤토리가 이후 모든 산출물의 기준 좌표가 된다.

  ## 산출물 1: 수치 검증 테이블
  각 행: 수치 | 회차 식별자 | 측정 조건(VU, 정원, 락 전략, accept-count, syn_backlog, 네트워크) | p95 기준(성공만/전체) | 로그 보유 수준 | 출처
  대상 수치:
  - 전략별(A 조건부 / B 낙관 / C 비관) success, full, conflict, drop, checks, p95(전체/성공 구분)
    — VU 레벨은 회차별 실제 그리드 기준. 회차 간 VU 그리드가 다르면 "공통 VU 레벨"(예: 200)과 "일부 회차에만 있는 레벨"을 구분 표기
  - accept-count 기본값 vs 256 전후의 한계 VU, drop 수, SYN cookie 발생 여부
  - SYN/accept 큐 관련 커널 지표 (SYN-RECV 카운트, acceptQ 수치, ListenOverflows/ListenDrops 등 — 존재하는 회차에서만)
  - saturation point, breaking point 관련 수치
  - RTT 관련 수치 (측정값인지 1회 관측인지 구분)

  ## 산출물 2: 테스트 타임라인 및 비교 가능성 매트릭스
  - 회차를 시간순 정렬: 회차 | 날짜 | 변인 | VU 그리드 | 핵심 결과 1줄 | 유효성 판정
  - 유효성 판정 기준:
    [유효] 환경 통제 + 설정 확인됨 / [조건부] 일부 불명 / [무효] 환경 미통제 또는 설정 초기화 의심
  - 비교 가능성 매트릭스: 어떤 회차끼리 직접 비교 가능한가?
    직접 비교 조건: 동일 VU 그리드 + 동일 설정 + 동일(또는 통제된) 네트워크
    ※ VU 그리드가 다른 회차 간 비교는 "공통 VU 레벨에서만 부분 비교 가능"으로 표기
  - ABC 3전략 최종 비교표(정원 100, VU 200/400/800)가 어느 회차 조합에서 나온 것인지 특정

  ## 산출물 3: connection reset 인과 체인
  "관찰 → 가설 → 검증 방법 → 결과(근거 로그 인용) → 판정(채택/기각)" 형식.
  - Tomcat 스레드 포화 가설 → 기각 근거 (스레드 메트릭 수치)
  - accept queue 오버플로 가설 → 검증 근거 (acceptQ 수치, accept-count 설정)
  - SYN queue 오버플로 가설 → 채택 근거 (SYN-RECV, syncookie 발생)
  - 클라이언트 네트워크 RTT 교란 변수 → 확인 근거 (회차 간 RTT 비교)
  - 각 단계에서 "당시에는 로그가 없어서 사후 추정인 부분"과 "로그로 직접 확인된 부분"을 구분 표기
    ※ 이 구분이 중요함: 커널 로그는 후반부터 찍었으므로, 초기 회차의 원인 설명은 후반 회차 로그로부터의 역추정일 수 있음. 역추정이면 역추정이라고 명시.

  ## 산출물 4: 사용 불가/불확실 수치 목록
  - 기록 불완전, 환경 미통제, 설정 초기화 의심 회차의 수치
  - 로그 없이 회고 기억에만 의존하는 수치
  - VU 그리드 불일치로 직접 비교가 성립하지 않는 비교 서술
  - 각 항목: 수치/서술 | 사용 불가 이유 1줄 | 대체 가능한 검증된 수치(있다면)

  ## 산출물 5: 기존 문장 클레임 검증
  아래 문장들의 수치·주장을 원본 기록과 대조하여 판정한다.
  각 클레임: 원문 | 판정(정확/부정확/기록 없음/부분 정확) | 근거(출처) | 수정 제안
  - "k6로 20여 회 비교 측정" → 실제 총 회차 수는? (전략별·설정별 분해. 회고 기준 11+4+4=19회와 대조)
  - "완료 요청 p95 전 구간 우세" → 공통 VU 레벨 각각에서 A가 B, C를 모두 이겼는가? VU 그리드가 다른 회차는 어떻게 처리했는가?
  - "드롭 수와 커널 카운터를 1건 단위까지 대응" → 실제 1:1 대응 가능한 로그가 존재하는가? 어느 회차인가?
  - "accept-count 튜닝(100→256)으로 큐 오버플로 드롭 제거" → '제거'인가 '감소'인가? 튜닝 후 회차에서 drop 0이었는가?
  - "핫스팟 RTT 41ms" → 측정값인가 1회 관측인가? 출처는?
  - "낙관락 VU200 성공 64/100 (정원 미달)" → 어느 회차이며 환경 통제된 회차인가? 재현된 적 있는가?
  - "raw 라벨↔전략 매핑이 세션마다 달랐다" → 매핑 오류 가능성이 있는 회차 목록과, 최종 비교표에 사용된 회차의 매핑 확인

  ## 크로스체크 (완료 전 필수 자가 검증)
  - 회차 인벤토리에 모든 테스트가 포함되었는가? 누락 의심 회차는?
  - 산출물 1의 모든 수치에 출처와 로그 보유 수준이 붙어 있는가?
  - p95는 전 항목에서 성공/전체 기준이 구분되어 있는가?
  - 초기 회차(커널 로그 없음)의 서술에 "역추정" 표기가 되어 있는가?
  - VU 그리드가 다른 회차 간 비교에 "부분 비교" 표기가 되어 있는가?
  - 산출물 5의 판정이 산출물 1·2의 데이터와 모순되지 않는가?
