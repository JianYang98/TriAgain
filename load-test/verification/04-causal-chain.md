# 04 — Connection Reset 인과 체인 (산출물 3)

> 형식: 관찰 → 가설 → 검증 방법 → 결과(근거 로그) → 판정.
> 각 단계에 **〔직접 확인〕**(그 시점 로그 존재) vs **〔사후 역추정〕**(후반 회차 로그로부터의 소급) 표기.
> 핵심 주의: **커널 로그(nstat·ss)는 07-01 3차부터, ss 라이브는 06-23부터만 존재.** 04월~06-22 회차의 원인 서술은 전부 역추정이다.

## 0. 최초 관찰 (04-17)

- 관찰: 비관락 vu200에서 19건, vu300에서 100건이 201도 409도 아님. 〔직접 확인 — 단 k6 HTML의 Failed Checks 수치뿐〕
- 이 시기의 "conn_reset"은 **측정된 메트릭이 아니라 파생값**: conn_reset = VU − success − full. raw JSON 없음, 에러 라벨 없음 [`crew-rush-connreset.html` L44~47, 04-17 HTML 4개 재확인 — "conn_reset" 메트릭 부존재]. 〔직접 확인〕
- 당시 문서의 원인 서술: "Tomcat threads.max=200 + accept-count=100 기본값… 락까지 도달하기 전에 TCP 레벨에서 탈락" [`07_crew-rush.md` L94~96] — **서버측 관측 없이 설정값 역산으로 쓴 해석**. 문서 스스로 후일 명시: "'정확히 accept-queue 100 초과가 원인'은 해석이지 측정값이 아니다" [`crew-rush-connreset.html` L117~120]. 〔사후 역추정임이 문서로 확인됨〕

## 1. 가설 A — Tomcat 워커 스레드 포화 → 기각

- 가설: "300 VU → 200 스레드 소진 → 나머지 거절" [`07_crew-rush.md` L96, `crew-rush-vu-scaling.html` L110 "threads.max 200 — 응답 200건 = 정확히 일치 ⭐ 범인"]. 〔당시엔 스레드 게이지 없음 — `crew-rush-connreset.html` L214 "Tomcat 워커 스레드 게이지가 없다. '스레드 200 포화'는 역산(추정)"〕
- 검증 방법: 07-01부터 Prometheus `tomcat_threads_busy_threads` 실측.
- 결과: 07-01 3차 busy max **48/200** [`0701_3번재비관락-결과.md` §7.2] · 07-03 5차 busy max 194~**196/200**(도달했으나 drop은 7뿐, 즉 스레드 포화≠드롭) [`0703_프로메테우스-실측-..md` §2] · C10 busy max 113 · C11 busy 109(단일 스크레이프). 드롭 발생 런에서 busy가 낮은 사례 다수.
- **판정: 기각** — "앱 어디에도 드롭의 흔적이 없음 = 드롭은 앱에 도달하기 전 커널에서 소멸" [`INTERVIEW-EPISODE..md` §④ 1차 서술, 원 근거는 07-01 Prometheus]. 〔직접 확인 — 07-01 이후. 04월 회차에 대해서는 역추정〕

## 2. 가설 B — HikariCP 풀 고갈 → 기각 (드롭 원인으로서)

- 가설: 후속 카드 초안 "풀 고갈 → conn_reset" [`HANDOFF-INTERVIEW.md` §0].
- 검증: `hikaricp_connections_timeout_total` 전 구간 **0** (Day1~6 누적 실측 [`00_environment.md` L56~59], 07-01 [`server-metrics-facts-20260701.md`], 이후 전 회차). acquire 대기는 큼(742ms~1.94s)이나 **timeout 0 = 풀이 막힌 적 없음**.
- **판정: 기각** — "acquire 742ms ≈ vu300 p95 → 지연의 대부분은 풀/락 대기(=지연 원인)이지 드롭 원인이 아니다. 드롭(status 0)은 액추에이터에 안 보인다 — 앱에 닿기 전 발생" [`비관락-총합결과-20260701.html` §7]. 〔직접 확인 — 07-01 이후〕
- (부기) HANDOFF 문서도 동일 정정: "실측은 HikariCP timeout 0… 정확히는 Tomcat 스레드/연결 한계" [`HANDOFF-INTERVIEW.md` §5] — 단 이 "Tomcat 한계" 표현 자체도 §1에서 기각됨.

## 3. 가설 C — CPU 크레딧 소진 → 기각

- 가설: 06-23 측정분산 초판 — "자정 런은 크레딧 바닥 → 스로틀 → drop, 아침 회복 → drop 급감" [`비관락-측정분산-20260623.html.20260623-credit정정.bak` §7 — 초판은 "CloudWatch 직접 대조 안 함" 미검증 고지 포함].
- 검증 방법: CloudWatch CPUCreditBalance 확인.
- 결과: "측정 전구간 만탱크(**288**)" → 정정본에서 크레딧 문단 전체 삭제·교체 [`비관락-측정분산-20260623.html` 정정 배너 + bak diff]. 저녁 연속 부하 직후에도 drop 0(휴식 무관 반증).
- **판정: 기각** 〔직접 확인 — 06-23〕

## 4. 가설 D — accept 큐(backlog=100) 오버플로 → **채택 (06-23 시기의 층)**

- 관찰: 같은 VU200 6런에서 drop 97→93→90→82→9→0 요동, succ=10 불변, full+drop=190 보존 [`비관락-측정분산-20260623.html` §5].
- 검증 방법: 서버 라이브 진단(06-23 아침) — ss·nstat·sysctl·ps.
- 결과: `ss -ltn :8080` **Send-Q=100**(실효 accept 큐 깊이) · `sysctl somaxconn`=4096(여유) · `nstat ListenOverflows=ListenDrops=625` · ps로 PESSIMISTIC 확정 [`비관락비교문서-20260623.html` L146~152]. 〔직접 확인 — **커널 층 최초의 직접 증거**〕
- **판정: 채택(당시 층)** — "범인은 순전히 큐 깊이. accept-count는 전 측정 구간에서 한 번도 상향된 적 없음(설정·git·기동인자 전수 확인)" [같은 문서 L152].
- ⚠️ 소급 한계: 이 진단으로 04월·06-19·06-22의 드롭까지 accept 큐로 단정하는 것은 **역추정**이다(그 시점 커널 로그 없음). 07-01 이후 "같은 커널에서 층이 회차마다 다름"이 실증되면서(아래 §5) 소급 단정은 더 위험해짐.

## 5. 가설 E — 층은 하나가 아니다: SYN 큐(수립층) → 채택 (07-01 이후의 층)

- 관찰: 07-01 3차 — ListenOverflows **Δ0**(52분 창)인데 drop 83·98 발생.
- 검증 방법: `nstat -asz` 1초 시계열을 k6 런 완료 시각에 초 단위 귀속(**07-01 3차에서 최초 도입**).
- 결과: TCPSynRetrans 스파이크 **+83**(20:25:22)·**+100**(20:27:38) = k6 join_dropped 83·98과 초·건수 일치 [`0701/nstat-ts-201300.log` 직접 재확인 + `0701_3번재비관락-결과.md` §7.4]. 〔직접 확인〕
- 정밀화(회차 누적):
  - 07-02 4차: **한 세션에서 두 층 동시 관측** — vu200#2 Overflow+141인데 drop 0(전량 흡수) / vu300 drop 16 = AttemptFails+16 = SYN-RECV 16 (= nstat 문서 기준 SyncookiesFailed·OutRsts +16도 일치) → **"오버플로 ≠ 드롭"** [`0702_비관락4차-결과.md` §9, `20260702_nstat_움직인카운터.md`]. 〔직접 확인〕
  - 07-03 5차: Overflow +2,239 전량 쿠키·재전송 흡수(지연으로만 발현), 유일한 영구 드롭 vu700 7건 = **7개 독립 관측 수렴** [`0703_..terminal.md` §5]. 〔직접 확인〕
  - 07-04~07-07: 드롭 등식 확정 — **AttemptFails(+EstabResets)=드롭**, C11에서 tcpdump까지 6채널 0오차(In RST 592=드롭, Out RST 선행 592/592) [`0707_..C11.md` §2·§6]. 〔직접 확인〕
- **판정: 채택** — 256 이후의 드롭은 전부 SYN 수립층(syncookie 폴백 → 검증 실패 → 서버발 RST) [`0707_accept-count-100vs256-..md` §0-3].
- 메커니즘 잔여 미확정: C10의 "지연 RST"(~0.5s 후 RST)는 nstat 3종만 수집돼 판별 불가로 종결 [`0705_로그상태분석_..C10.md` §7.3] 〔기록 없음으로 남김〕.

## 6. 교란변수 — 클라이언트 RTT → 확인됨 (3점 + 통제쌍)

- 관찰: 같은 설정(256)인데 6차(07-03)는 vu700까지 드롭 0, A1(07-04)은 vu500부터, C7(07-04)은 vu300부터.
- 검증 방법: 무부하 connecting avg를 기저 RTT 프록시로 세션 간 비교 + 같은 밤 교차측정(A1↔C7) + C7↔C9 요청별 타임라인 재구성.
- 결과: **41ms(C6)→드롭 0 · 25ms(A1)→vu500 · 12ms(C7·C9)→vu300** — "회선이 좋을수록 드롭 개시 VU가 내려가는 역설의 3점 확인" [`0704_비관락7차-원자적update-비교.md` §4.1]. 느린 회선은 SYN 재전송 사다리(connecting max 5.5/10.4/15.3s)가 도착을 11~15초로 펴서 순간 동시성을 깎음 [`0703_비관락6차-결과.md` §4] — 6차의 "무손실"은 개선이 아니라 도착 스미어링(p95 급락 1889→937→476→407도 동일 원인) [같은 문서 §3]. A3(카페, Overflow+1443·드롭0)↔A4(집, 드롭 473) 발현형 정반대도 네트워크 제1후보 [`0706/A4/..결과.md` §8-1]. 〔직접 확인 — 07-03 이후. 단 회선 종류(핫스팟 등)는 미기록·추정 👤〕
- 잔여 미종결: C10의 개시 vu500 후퇴는 RTT로 설명 안 됨(C10 발사 폭이 C11과 동일하게 예리) → 실효 SYN큐 한도(무기록 조치) 소거법 추정, 닫으려면 256↔512 재현실험 [`0707_..드롭차이-분석.md` §3·§7].
