## C-4. "accept-count 튜닝(100→256)으로 큐 오버플로 드롭 제거"

- **판정: 부분 정확(오해 소지 큼) — '제거'가 맞는 대상은 'accept 큐 오버플로발(發) 드롭'뿐. 총 드롭은 제거되지 않았다.**
- 근거:
  - 튜닝 직후 6차: 전 8런 drop 0·Overflow 0 (시리즈 최초) — **그러나 RTT 41ms 스미어링 동반**(U-4), 이후 같은 256에서 C7/C9/C11/A2/A4 모두 vu300부터 드롭 재발(SYN층).
  - ListenOverflows는 256 이후 대부분 0 — **예외 A3: +1,443 재발**(드롭 0, 전량 흡수·acceptQ 257/256) [`nstat-ts-172854-A3.log`]. "오버플로 제거"도 절대적이지 않음.
  - 정본 표현: "드롭 개시 VU 한 스텝 상향(vu200→vu300, 두 전략 공통) + vu200 정화(비관 33→0·원자적 83→0) + 병목이 accept 큐→SYN 큐로 이동" [`0707_accept-count-100vs256-..md` §0].
  - 🔴 이 前後 비교의 "원자적 前" 열은 **무효 확정**(07-07 👤 CCC=비관 확정, U-1) — 원문의 "두 전략 공통"은 비관만 지지로 축소. 비관 前後(CC 2차→C11)는 유효하며 CCC가 2번째 재현으로 추가돼 오히려 강화(vu200 개시 33·83).
- 수정 제안: "제거" → "드롭 개시 부하 한 스텝 상향 + vu200 완전 정화, 병목 층은 SYN 큐로 이동"으로 교체 (튜닝 후 drop 0이었던 것은 6차 단일 세션·RTT 조건부). 전후 효과 주장은 **비관락 데이터로만** 서술.

## C-5. "핫스팟 RTT 41ms"

- **판정: 수치는 실측·"핫스팟"은 기록 없음.**
- 근거: 41ms의 실체 = 6차 무부하 구간(vu20~50) `http_req_connecting` avg **40.9~43.7ms** — k6 런 단위 집계(1회 관측 아님, ping 아님) [`0703_비관락6차-결과.md` §4]. 회선 종류는 "클라이언트 측 네트워크(Wi-Fi/핫스팟 등) 차이로 **추정** 👤" [같은 문서 §9.6] — 핫스팟 확정 기록 없음.
- 수정 제안: "RTT 41ms(무부하 connecting avg 실측)인 느린 회선" — 회선 종류 미기록 명시. [`docs/k6-insight/..수치검증.md` §1-3과 동일 결론]
