# RPS 테스트 프로세스

[TIER 판정] Tier: 3 | 근거: 테스트 크루·리더를 생성하고 검증하는 DB 트랜잭션 추가 | 판정자: orchestrator | 2026-11-18

> 상태: 로컬 구현·검증 단계. EC2 적용은 7절의 배치 단계에서 진행한다.
> 명령과 SQL은 `load-test/scripts/prepare`, `load-test/sql/prepare_crew.sql` 두 파일을 상대 경로가 유지되도록 함께 둔다.

## 1. 확정한 흐름과 역할

**prepare로 크루 생성·검증·기록 → 사용자 수집 시작 → 사용자 k6 실행 → 사용자 결과 확인 → 사용자 수집 종료 → 원하는 시점에 수동 정리.**

- 운영 앱 EC2와 테스트 앱 EC2 모두 같은 prepare 명령을 사용한다. 크루를 만들 DB는 각 EC2에 명시적으로 설정한다.
- prepare가 크루와 리더를 DB에 생성하고 초기 상태를 검증한다. 사용자가 SQL을 복사해 실행하는 단계는 없다.
- 화면에 결과를 출력하고 KST 날짜별 로그 **하나**에 누적 append한다.
- run.json·생성 SQL·검증 SQL·결과 JSON·실행별 폴더는 별도 산출물로 만들지 않는다.
- 워밍업과 본 측정은 각각 새 run·새 크루로 준비한다. 조건은 서로 달라도 된다.
- 이미 요청을 보낸 크루는 재시험에 재사용하지 않는다.
- 수집 ON/OFF와 k6 실행은 prepare가 하지 않는다. 사용자가 각각 실행한다.
- Redis 초기화·비동기 반영 확인과 수집 종료 시점은 사용자가 판단한다.
- 삭제는 사용자가 별도 스크립트로 처리한다. 크루 ID 또는 KST 생성 날짜와 테스트 식별 정보로 범위를 정한다.

## 2. 입력과 이름 규칙

Python 3.9 이상과 `psql`이 필요하다. 저장소 루트에서 실행 예시는 다음과 같다.

```sh
load-test/scripts/prepare --config /path/to/prepare.json --rps 100 --capacity 10 --requests 1000
load-test/scripts/prepare --rps 50 --capacity 100 --requests 1000 --warmup
```

| 입력 | 정의 |
|---|---|
| --rps | 필수 양의 정수. 목표 초당 요청 수이며 실제 달성 RPS는 아니다. |
| --capacity | 필수 양의 정수. 리더 포함 크루 정원. 첫 버전 도구 한도는 기존 fixture 범위인 1~1000으로 한다. 일반 서비스의 정원 규칙을 바꾸지 않는다. |
| --requests | 필수 양의 정수. 계획한 가입 요청 수이며 사용자 수·성공 가입 수가 아니다. |
| --config | 접속 설정 파일 경로. 생략하면 PREPARE_CONFIG 환경 변수에서 읽는다. |
| --warmup | 선택. 있으면 워밍업, 없으면 본 측정. |

초기 인원은 리더 1명으로 고정한다. RPS와 요청 수는 로그에 기록할 실행 계획이며, 크루 생성 시 부하를 보내거나 사용자·토큰을 만들지 않는다.
각 가입 요청에 서로 다른 사용자가 필요한지는 k6 시나리오에서 확인한다.
정원 10·초기 1명이면 가입 가능 자리는 9개다. 다른 요청의 응답은 정원·중복·오류 조건 등에 따라 달라진다.
RPS·요청 수의 구현상 허용 정수 범위는 명시적으로 검사한다. 지원되지 않는 값은 DB 쓰기 전에 거절한다.

Asia/Seoul 시각을 준비 시작 때 한 번 정하고 이름·로그 날짜·DB 생성 시각에 같은 기준을 사용한다.

| 항목 | 본 측정 예시 | 워밍업 예시 |
|---|---|---|
| 실행 ID | 20261118-153000-rps100-cap10 | 20261118-152000-rps50-cap100-warmup |
| 크루 ID | dbb-20261118-153000 | dbb-20261118-152000 |
| 크루 이름 | 테스트크루-20261118-153000 | 테스트크루-20261118-152000 |

- 크루 ID는 19자, 이름은 21자다. DB ID 36자·기존 SQL ID 35자, API 이름 50자·DB 이름 255자 제한 안이다.
- 임의 접미사와 main/warm 접미사를 크루 ID에 붙이지 않는다.
- 같은 초에 재실행해도 같은 크루 ID이므로 중복은 실패 처리한다. 기존 데이터 수정·덮어쓰기·삭제는 하지 않는다.
- 이전 로그에 해당 크루 ID가 있거나 DB에 크루·연관 잔재가 있으면 재사용하지 않는다. 기록을 제거한 뒤까지 영구 유일성을 보장하는 별도 대장은 만들지 않는다.

## 3. 단계별 절차

### 1단계 — prepare 사전 확인

사용자가 입력 조건과 설정된 대상 DB를 확인해 prepare를 실행한다.
prepare는 입력, 필수 실행 도구, 명시된 DB 접속 대상, 로그 경로 쓰기 가능 여부를 먼저 검사한다.
DB 연결 기본안은 각 EC2에 전용 설정을 한 번 두고 PostgreSQL 클라이언트 `psql`로 접속하는 방식이다. 설정에는 허용 호스트·포트·DB 이름·DB 사용자·스키마와 로그 보관 루트를 둔다. 비밀번호는 실행 계정의 `~/.pgpass`에 대상별로 등록하고 파일 권한은 `0600`으로 둔다.

접속 설정 파일 예시의 값은 배치 대상에 맞춰 바꾼다. 두 번째 실행 예시처럼 `--config`를 생략하려면 `PREPARE_CONFIG`에 이 파일의 절대 경로를 지정한다.

```json
{
  "host": "db.example.invalid",
  "port": 5432,
  "database": "triagain_dbb",
  "user": "prepare_user",
  "schema": "public",
  "allowed_hosts": ["db.example.invalid"],
  "sslmode": "verify-full",
  "log_root": "/path/to/load-test-logs"
}
```

`verify-full`을 쓸 때는 실행 계정에 대상 DB 인증서를 검증할 CA를 설치한다. 이 설정 파일은 EC2마다 미리 준비하며 일일 실행 로그와 별개다.

prepare는 설정한 접속값과 TLS 설정으로 psql을 호출한다. 접속한 세션에서 DB 이름·사용자·스키마를 확인한 뒤 같은 세션에서 생성과 검증을 진행한다. 설정 누락, 대상 불일치, 인증 실패 시 쓰기 전에 종료한다. 실행하는 EC2의 이름으로 DB를 추정하거나 다른 DB로 재접속하지 않는다.

로그 경로는 `<보관 루트>/prepare/YYYYMMDD.log`다. 기본안은 실행한 EC2의 로컬 디스크에 저장하는 것이다. 두 호스트에서 같은 DB를 대상으로 실행하면 로컬 잠금은 공유되지 않으므로 같은 초의 크루 ID 충돌은 DB 기본 키와 트랜잭션으로 처리한다.
로그 파일을 열거나 실행 간 잠금을 확보할 수 없으면 DB 쓰기 전에 실패한다.
같은 보관 루트에서는 prepare 실행을 직렬화해 중복 검사와 로그 블록이 섞이지 않도록 한다.

### 2단계 — DB 생성·초기 검증

하나의 트랜잭션으로 크루 1행과 리더 멤버 1행을 생성하고 커밋 전에 초기 상태를 검증한다.
기존 SQL의 내용은 참고하되 그대로 호출해 제한을 우회하거나 기존 파일을 수정하지 않는다.

첫 버전 fixture 기준:

| 항목 | 값·조건 |
|---|---|
| 생성자·리더 | 기존 활성 계정 loadtest-leader. 없거나 탈퇴 상태면 실패. prepare가 사용자를 생성·복구하지 않음 |
| 인원 | max_members는 입력값, current_members=1, 리더 멤버 행 1건·LEADER 역할 |
| 상태·공개 여부 | RECRUITING, PUBLIC |
| 인증·카테고리 | TEXT, ETC, 테스트용 목표·인증 설명 |
| 날짜 | 크루 시작일은 KST 생성일 +7일, 종료일은 크루 시작일 +30일. 시작일이 되면 활성화 대상이 될 수 있으므로 그 전에 정리 일정을 확인 |
| 기타 | allow_late_join=false, 초대 코드 영숫자 6자·UNIQUE, 나머지 필수 컬럼·기본값은 실제 스키마에 맞춤 |

이 fixture는 일반 크루 생성 API의 정원·날짜 검증을 거치지 않는 테스트 전용 데이터다. 서비스 도메인 규칙을 확장한다는 뜻이 아니다.
초대 코드·멤버 ID 생성 방식은 구현에서 충돌을 검사하며, 충돌 시 전체 트랜잭션을 실패시킨다.
입력값은 SQL 매개변수 등 안전한 방식으로 전달하고 문자열 결합으로 실행하지 않는다.

커밋 전 확인:

- 크루 ID·이름·생성자·정원·날짜·상태가 계획과 일치한다.
- 멤버 행은 리더 1명뿐이고 current_members와 실제 멤버 수가 일치한다.
- 동일 크루 ID의 이전 멤버·챌린지·인증·업로드 등 잔재를 새 생성으로 덮지 않는다.
- 검증에 실패하면 생성된 크루·리더 행을 모두 롤백한다.

### 3단계 — 화면 출력·로그 저장 후 prepare 종료

DB 커밋 확인과 결과 로그 저장까지 성공해야 **크루 준비 완료**를 출력하고 성공 종료한다.
종료란 터미널에서 다음 명령을 입력할 수 있게 된다는 뜻이다. 크루는 DB에 남는다.

화면과 일일 로그에 아래 정보를 남긴다. 로그는 기존 내용을 유지하고 구분선으로 새 블록을 추가한다.
한 회차의 시작 기록과 결과 기록 사이에는 빈 줄 하나를 둔다.

```text
[2026-11-18 15:30:00 KST]
실행 ID: 20261118-153000-rps100-cap10
크루 ID: dbb-20261118-153000
크루 이름: 테스트크루-20261118-153000
목적: 본 측정
대상 DB: <호스트>:<포트>/<DB>/<스키마>
목표 RPS: 100
크루 정원: 10명
초기 인원: 1명 — 리더
총 요청 수: 1000회
가입 가능한 자리: 9명
DB 결과: 커밋 확인
검증: 통과
결과: 크루 준비 완료
로그: <보관 루트>/prepare/20261118.log

TARGET_RPS=100 TOTAL=1000 RUN_ID=20261118-153000-rps100-cap10

------

[다음 실행 시각]
다음 실행 내용...
```

- prepare 로그는 준비 기록이다. k6 결과와 수집 원본을 이 로그에 합치지 않는다.
- 인증 토큰·DB 비밀번호·비밀값이 포함된 접속 문자열을 기록하지 않는다.
- 사전 확인 뒤 DB 쓰기 전에 시작 기록을 남기고, 종료 결과를 추가한다. 종료 기록 없는 시작은 완료로 해석하지 않는다.
- 성공, 롤백된 실패, DB 반영 불명, 커밋 후 기록 실패를 구분한다. 실패는 비정상 종료 코드로 반환한다.
- 파일을 열 수 없으면 화면에 원인을 출력하고 DB를 변경하지 않는다. 잘못된 입력으로 ID가 미확정이면 로그에 ID 미확정으로 표시할 수 있다.
- 커밋 응답 유실·프로세스 강제 종료·커밋 후 디스크 오류는 DB와 파일을 함께 롤백할 수 없다. 확인 가능한 DB 결과와 기록 오류를 stderr에 출력하고 자동 재생성·삭제하지 않는다.
- 기록이 끝나기 전에 프로세스가 죽으면 최종 로그가 없을 수 있다. 사용자가 크루 ID로 DB를 확인한다.
- 자정을 넘어 끝나도 시작 때 정한 KST 날짜의 로그에 기록한다. 로그 이외에 일시적인 실행 잠금 파일은 사용할 수 있다.

### 4단계 — 사용자 수집 시작

사용자가 관측 대상·컨테이너를 확인하고 출력된 실행 ID로 기존 수집기를 켠다.
정상 수집과 실제 표본 기록을 확인하고 부하 전 기준 구간을 확보한다. 길이는 실험 목적·수집 주기에 맞춰 정한다.
부분 시작 실패 시 이미 켜진 항목이 있을 수 있어 상태를 확인한다.
ON/OFF 명령은 `collectors/MANUAL-COLLECT.md`를 따른다. 배치 상태·현재 수집 성공은 실행 환경에서 확인한다.

### 5단계 — 사용자 k6 실행

러너 EC2의 `~/triagain-k6`에서 진행한다. 세션을 열 때 한국 날짜를 한 번 지정한다.
다음 날 같은 세션을 이어가려면 오늘 날짜를 다시 계산하지 말고 원래 값(예: `export SESSION_DATE=20261118`)을 지정한다.

```bash
export SESSION_DATE="$(TZ=Asia/Seoul date +%Y%m%d)"
```

`BASE_URL`, `TOKENS_FILE`(절대 경로), `PRE_VUS`는 러너에서 한 번 설정한다. 필요하면 `MAX_VUS`와 `REQ_TIMEOUT_SECONDS`도 설정한다.
수집이 정상인지 확인한 뒤, prepare가 출력한 실행 ID·목표 RPS·요청 수를 전달한다.

```bash
cd ~/triagain-k6
TARGET_RPS=100 TOTAL=1000 RUN_ID=20261118-155611-rps100-cap10 \
  ./load-test/scripts/run-db-rps-baseline.sh
```

실행 명령이 `load-test/results/<SESSION_DATE>/<RUN_ID>/`를 만든다.
그 안의 `k6-command.txt`는 실행 명령, `k6-console.log`는 화면에도 나오는 콘솔 로그, `k6-rps-summary.json`은 종료 요약이다.
콘솔 로그 맨 아래에는 목표와 실제 평균 RPS, 전송·미전송 건수, VU, HTTP 401과 실패 사유가 나온다.
시각별 지표가 필요한 실행은 위 명령의 첫 줄에 `DETAIL=1`을 붙인다. 같은 실행 폴더의 `k6-metrics.jsonl.gz`에 VU, 미전송, 응답 시간의 시각별 지표가 저장된다.
날짜가 비어 있거나 잘못됐으면 폴더 생성 전에 멈춘다. 같은 실행 폴더가 있으면 기존 결과를 보존하고 중단한다.
k6 종료 코드는 그대로 전달한다. 초기 설정 오류 등으로 요약이 생성되기 전에 실패한 경우 콘솔 로그부터 확인한다.
기존 실행기는 계속 `results/raw/`를 사용한다.

### 6단계 — 사용자 결과 확인·수집 종료

k6 종료 후에도 수집을 이어갈 수 있다. 진행 중 요청·Redis 비동기 반영 등 필요한 확인은 사용자가 수행한다.
prepare에는 Redis 초기화, 자동 drain 판정, 고정 대기, 수집 자동 종료를 넣지 않는다.
필요한 최종 DB 증거와 로그·지표를 보존하고 사용자가 수집을 끈다.
목표·실제 RPS, 성공 가입, 정원 초과, 중복, 기타 오류를 구분한다. 확인 불가 결과는 불명으로 남긴다.

### 7단계 — 사용자 수동 정리

원하는 시점에 사용자 별도 스크립트로 정리한다.
크루 ID 지정 또는 KST 생성 날짜와 dbb 접두사·테스트 생성자로 대상 범위를 한정할 수 있다.
연관 DB 데이터와 Redis 등 외부 상태는 실제 시나리오에 맞춰 사용자가 확인한다.
자동 삭제·정리 상태표·삭제 스크립트 구현은 이번 범위에 없다.

## 4. 구현 범위

### 포함

- 독립 Python 진입점 `load-test/scripts/prepare`와 전용 SQL `load-test/sql/prepare_crew.sql`.
- 입력·대상 DB·로그 사전 검증, KST 명명, 중복 거부.
- 크루·리더 생성, 초기 상태 검증, 단일 트랜잭션·롤백.
- 화면 출력, 날짜별 로그 append, 동시 실행 직렬화, 실패·불명 구분.
- [신규] 도구 테스트와 실행 방법을 이 문서에 동기화.

### 제외

- 기존 생성·삭제 SQL, stage.py, k6, 수집기·모니터링 도구 수정.
- Java 도메인·API·스키마·마이그레이션·인증·스케줄러 변경.
- 사용자·토큰 생성, Redis 준비·반영 대기, 수집 ON/OFF, 부하 실행, 자동 재시도·삭제.
- JSON·SQL 등의 실행별 산출물과 별도 실행 폴더 생성.
- 운영 DB 실행, 실제 EC2 배치, 서버·컨테이너 상태 변경. 향후 별도 실행 범위로 다룬다.

구현은 테스트 크루 생성·초기 검증을 하나의 DB 트랜잭션으로 실행하므로 Tier 3로 판정했다.
도메인·스키마·운영 연결 설정 등 변경이 필요하면 멈추고 범위를 다시 합의한다.
실제 파일은 이 도구 저장소 워크트리에 추가하며 기존 미커밋 변경은 보존한다.

## 5. 구현 검증 조건과 완료 기준

구현 검증은 mock만으로 완료 처리하지 않는다. PostgreSQL 검증은 운영·공유 DB가 아닌 격리된 테스트 DB에서 한다.

| 검증 | 합격 조건 |
|---|---|
| 정상 생성 | 입력한 정원·명명 규칙, 크루 1행·리더 1행·역할·날짜·인원 모두 일치, 커밋·로그 성공 후에만 성공 종료 |
| 경계값·오입력 | capacity 1·1000 허용, 0·1001·음수·소수·누락 거절. rps·requests도 유효·무효 값을 대조하고 거절 시 DB 무변경 |
| 대상·리더 가드 | 허용 DB 대조 불일치, 접속 불가, 리더 없음·탈퇴면 생성 0건 |
| 충돌·잔재 | 기존 크루·멤버 잔재·초대 코드 충돌·이전 로그의 동일 ID면 실패, 기존 행·로그 내용 보존 |
| 트랜잭션 | 리더 INSERT 실패 또는 초기 검증 불일치를 주입해 크루·리더 부분 생성 0건 증명 |
| 누적 기록 | 같은 날 다른 시각 2회 실행 시 같은 일일 로그에 조건·결과·구분선 보존, JSON·SQL·실행 폴더 추가 생성 없음 |
| KST 경계 | 호스트 타임존과 무관하게 KST 날짜 사용, 자정 경계에도 시작 날짜 로그 유지 |
| 중복·동시 실행 | 같은 초 실행과 동시 append에서 덮어쓰기·부분 블록 혼합·중복 크루 생성이 발생하지 않음 |
| 기록 오류·불명 | 로그 사전 실패 시 DB 쓰기 0건, 커밋 후 기록 실패·커밋 응답 유실 시 성공 표시·자동 재시도 없음 |
| 민감값·범위 | 토큰·비밀번호 미출력, 로그/SQL 입력 안전 전달, 기존 도구·사용자·무관 크루·서버 상태 불변 |

민감성 확인: 가드·검증·트랜잭션 보장을 격리 사본에서 일부러 깨뜨려 관련 검증이 실패하는지 확인한다.
실제 PostgreSQL 검증 결과와 파일·로그 결과를 함께 보존한다. 연결 유실 등 일부 주입을 mock으로만 검증했다면 한계를 적는다.

완료 보고에는 실행 명령·PASS/FAIL·환경·미실행 조건을 적는다.
코드 언어에 맞는 구문·정적 검사, 신규 도구 테스트, 관련 저장소 필수 검사와 외부 AI 리뷰를 수행한다.
필수 검사를 못 돌렸다면 완료로 숨기지 않고 사유·영향을 남긴다. 문서 검증 PASS를 도구 실행 검증으로 표현하지 않는다.
EC2 실사용 검증은 별도 실행 범위에서 준비 전후 DB·날짜별 로그를 확인하고 수집·k6를 자동 시작하지 않는지 확인한다.

## 8. 사용자가 결정할 사항

1. **각 EC2에서 어느 DB에 만들 것인가?** 크루는 k6가 호출할 앱이 실제로 읽는 DB에 있어야 한다. 두 앱이 같은 테스트 DB를 쓰는지, 각각 별도 DB를 쓰는지, 운영 서비스 DB에 테스트 크루를 만들 필요가 있는지를 먼저 정한다. 운영 DB 쓰기가 필요하면 대상·권한과 운영 영향을 별도 범위로 검토한다.
2. **접속 계정과 로그 위치는 무엇인가?** 기본안은 각 EC2의 실행 계정이 psql과 pgpass를 사용하고 그 EC2의 로컬 보관 루트에 기록하는 것이다. 배치 전에는 대상별 DB 계정의 조회·생성 권한과 보관 루트의 절대 경로를 확인한다. 두 EC2의 이력을 한 파일로 모아야 한다면 저장 위치와 동시 기록 방식을 별도로 정한다.

사용자가 실행하는 명령은 prepare 한 번이며, 이후 수집과 k6는 기존 수동 절차를 따른다.
