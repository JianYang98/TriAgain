## 3. 런별 ss 소켓 피크 〔측정·파생〕

- **acceptQ = 0/256 전 런** — 완료 핸드셰이크 큐(accept 큐)는 한 번도 적재되지 않음. backlog 256 여유 충분. (5차는 101/100 오버플로)
- **ESTAB 피크 = VU+1 정확**(21/51/101/201/301/401/501/701; +1 = 모니터링 커넥션) — 전 VU 연결이 결국 수립됨. **결손 0 → 드롭 0의 독립 확증**.
- **SYN-RECV 피크 상승**: ≤200=0 → 300=6 → 400=140 → 500=147 → **700=209**. 반열림(SYN 수신, ACK 대기) 소켓이 SYN 큐에 쌓임 — **이번 차수 병목의 직접 지문**.
- LAST-ACK(서버가 FIN 보내고 최종 ACK 대기)은 100~181로 큼 — 요청당 연결 open/close 반복에 따른 teardown 체류. 매우 전이적이라 ss 샘플이 확률적으로 포착(vu100의 100은 teardown 버스트를 우연히 잡은 값).

## 6. 층 판정 〔분석〕

1. **병목 층 = SYN 큐 / SYN-ACK 재전송 (accept 큐 아님).** 근거: accept 큐는 미적재(ss `acceptQ=0/256`, nstat `ListenOverflows Δ=0`)인데 SYN-RECV는 vu700 209까지 적재되고 SynRetrans +1830. 완료 핸드셰이크가 accept 큐에 온 뒤가 아니라, **핸드셰이크 완료 자체(SYN-ACK↔ACK)가 지연**됐다. → k6 `http_req_connecting` 폭발(§4)의 원인은 accept 큐 대기가 아니라 **SYN 핸드셰이크 재전송 지연**.

2. **5차와 다른 층.** 5차 병목 = accept 큐 오버플로(`ListenOverflows +2239`) + vu700 영구 드롭 7(SyncookiesFailed 층). 6차 = SYN-ACK 재전송 지연, 드롭 0. **t3.micro 연결 수립 천장이 런마다 다른 층으로 발현**한다는 시리즈 공통 관찰의 새 사례.

3. **backlog 256 관측(👤 원인 미확정).** ss 전체 `acceptQ=*/256`(5차 `/100`). accept 큐 한계가 커진 것은 사실이나 변경 주체(`somaxconn`/Tomcat `accept-count`/앱 재배포 기본값/재시작)는 이 세션 미확인. 무오버플로 결과가 (a) backlog 확대 덕인지 (b) SYN 단계 백프레셔가 그 앞에서 유량을 조절해 accept 큐까지 몰릴 일이 없었던 것인지는 **backlog 설정 근거 확정 후에만** 구분 가능. — 재현·차수 비교 전 필수 확인.

4. **재전송 방향 가설(미확정).** vu500/700에서 신규 syncookies 0인데 SynRetrans 대량 = 서버가 SYN-ACK를 보냈으나 클라이언트 최종 ACK가 늦어 RTO 재전송했을 가능성. 이 경우 단일 k6 호스트의 송수신 포화가 ACK 지연에 기여했을 수 있다(클라이언트측 요인). 서버·클라이언트 어느 쪽 포화인지는 이 로그만으로 단정 불가 — **락/코드 요인은 아님**(정합성 완벽, §결과서 §5).
