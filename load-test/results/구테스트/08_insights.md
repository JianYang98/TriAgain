## 2. 핵심 인사이트 7가지

### 인사이트 1: "TPS 920"은 99.7%가 읽기였다

- `load-normal.js` 혼합 부하의 `http_reqs/s = 920`을 "TPS"라고 부르면 오해
- Endpoint 분해: GET 912/s (99.7%) + POST 3/s (0.3%)
- 유효 DB INSERT: 0.41/s (유저 50명 소진 후 409 지배)
- **교훈**: `http_reqs/s`는 네트워크 레벨 메트릭. 비즈니스 트랜잭션과 분리해서 보고해야 한다
- **조치**: Day 7에서 write-only 시나리오로 진짜 쓰기 포화 처리량 **약 480~490/s** 확정 (15초 구간 실측)

### 인사이트 2: `http_req_failed`는 서버 건강성 지표가 아니다

- k6 기본 threshold `http_req_failed`는 **HTTP 4xx도 실패로 집계**
- 409(UNIQUE 위반, 정원 초과) = 정상 비즈니스 거절인데 "6.82% FAIL"로 판정
- 같은 데이터가 판정 기준에 따라 FAIL/PASS 뒤집힘
- **교훈**: 도구의 기본값을 맹신하지 말 것. "우리 도메인에서 실패란 무엇인가"를 먼저 정의
- **조치**: `checks_failed` 기반 판정 기준 재정의. 서버 에러(5xx)만 실패로 집계

### 인사이트 3: 비관적 락(SELECT FOR UPDATE)은 정합성은 완벽, 확장성이 한계

Day 8 크루 러시 VU 스케일업 실험:

| VU | join_success | p95 | conn_reset |
|----|-------------|-----|------------|
| 50 | 10 (정확) | 175ms | 0 |
| 100 | 10 (정확) | 339ms | 0 |
| 200 | 10 (정확) | 492ms | 19 (9.5%) |
| 300 | 10 (정확) | 683ms | 100 (33.3%) |

- **데이터 정합성 100%** — 300명이 동시에 달려들어도 정원 초과 0건
- **p95 선형 증가** — VU당 ~2ms 추가 (직렬화 비용)
- **VU 200부터 Tomcat connection reset** — 락이 아니라 서버 동시 연결 한계
- **교훈**: 비관적 락은 "안전하지만 느린" 전략. Phase 1에서는 적정 기술, Phase 2에서 낙관적 락/Redis로 전환 필요

### 인사이트 4: 스케줄러 중복 실행이 감지 없이 발생한다

Day 8 스케줄러 적체 실험 (fail-expired 2연속 트리거):

| 실행 | 처리 건수 | 소요 시간 |
|------|----------|----------|
| 1차 | 2,500건 | 1,532ms |
| 2차 | 2,400건 | 1,457ms |

- `fixedRate` = 시작 기준 5분 → 처리가 5분 넘으면 **즉시 다음 실행 시작**
- 겹침 방지 없음 (`@SchedulerLock`, ShedLock 없음)
- `@Version` 없음 → 같은 row에 `SET status='FAILED'` 2번 실행해도 **예외 없음** (last-write-wins)
- **교훈**: 현재는 멱등한 UPDATE라 무해. 하지만 알림/새 사이클 생성 같은 부수 효과가 붙으면 **2중 실행 = 버그**
- **조치**: `fixedRate` → `fixedDelay` 변경 (코드 1줄, 겹침 원천 차단). 다중 인스턴스 시 ShedLock 도입

### 인사이트 5: HikariCP pool=10은 Phase 1에서 충분하다

- Day 1~8 전 구간 `hikaricp_connections_timeout_total = 0`
- 쓰기 부하(Day 7)에서 Pending 최대 140 → pool 포화, 하지만 timeout 없음
- `max_connections=79` 대비 pool=10 → 수평 확장 시 7 인스턴스까지 RDS 변경 없이 가능
- **교훈**: "DB 커넥션 풀부터 늘리자"는 흔한 오판. 실제 병목은 CPU/GC인 경우가 많다
- **조치**: Phase 1에서는 기본값 유지. 쓰기 TPS 향상 필요 시 pool 20-30으로 실험

### 인사이트 6: 쓰기 병목은 DB 커넥션 + GC이지 CPU가 아니다

Day 7 쓰기 부하 Grafana 관찰:

| 메트릭 | 읽기 부하 (Day 2) | 쓰기 부하 (Day 7) |
|--------|-----------------|-----------------|
| HikariCP Pending max | 76 | **140** |
| GC Pause max | 6.8초 | **4.6초** |
| CPU max | 100% | **85%** |

- 쓰기 시 CPU는 85%로 읽기보다 여유인데, HikariCP Pending은 2배
- 1 POST = SELECT 4-5 + INSERT 1 + UPDATE 1 = 6-7 DB ops → 커넥션 점유 시간이 길다
- GC Pause 동안 커넥션을 쥐고 있으므로 Pending 급등
- **교훈**: 쓰기 throughput 향상의 키는 (1) GC 튜닝으로 pause 줄이기, (2) pool 확장, (3) 트랜잭션 범위 최소화

### 인사이트 7: 환경을 먼저 의심하라

- Day 1~5까지 "t2.micro / 1 vCPU"로 알고 있었음
- Day 6에 IMDS 실측 → 실제는 **t3.micro / 2 vCPU burstable**
- TPS 920의 해석 자체가 달라짐 (1 vCPU 포화 한계 → 2 vCPU + 크레딧 영역)
- **교훈**: 측정 결과보다 측정 환경을 먼저 검증하라. "어디서 돌렸는가"가 틀리면 모든 해석이 틀린다

| Phase | 규모 | 전략 | 전환 트리거 |

| Phase | 전략 | 비고 |

| 2 (다중 인스턴스) | ShedLock + DB 기반 분산 락 | 수평 확장 시 필수 |

| 순서 | 튜닝 | 기대 효과 |

| 2 | HikariCP pool 20-30 | Pending 140 → 감소 |
| 3 | 인스턴스 스케일업 (t3.small) | CPU 여유 + RAM 2GB |
