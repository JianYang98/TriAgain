## 변경 사항

| 항목 | Before (비관적 락) | After (낙관적 락) |
|------|-------------------|-------------------|
| 전략 | `SELECT FOR UPDATE` | `findById` + version check 쿼리 |
| 충돌 처리 | 행 락 대기 (직렬화) | `WHERE version = ?` 실패 시 재시도 (최대 3회) |

**결론: 전 구간 정합성 100% — 낙관적 락도 정원 초과 0건.**

### 응답 시간 (p95)

| VU | Before (비관적) | After (낙관적) | 차이 |
|----|----------------|----------------|------|
| 50 | 175ms | 478ms | +303ms |
| 100 | 339ms | 670ms | +331ms |
| 200 | 492ms | 849ms | +357ms |
| 300 | 683ms | 1,260ms | +577ms |

**분석:**
- 낙관적 락이 전 구간에서 느림 — **재시도 비용**
- 비관적 락: 락 대기 후 1회 실행으로 끝남
- 낙관적 락: version 충돌 시 재시도 (최대 3회) → 누적 지연
- VU 300에서 p95 1.26초 — 1초 초과 (threshold FAIL)

### Connection Reset (핵심 차이)

| VU | Before (비관적) | After (낙관적) | 변화 |
|----|----------------|----------------|------|
| 50 | 0 | 0 | 동일 |
| 100 | 0 | 0 | 동일 |
| 200 | **19 (9.5%)** | **0** | **해소** |
| 300 | **100 (33.3%)** | **0** | **해소** |

**핵심 발견:**
- 비관적 락: VU 200부터 Tomcat connection reset 발생 (SELECT FOR UPDATE가 행 락을 잡고 대기 → 커넥션 점유 시간 증가 → Tomcat 동시 연결 한계 도달)
- 낙관적 락: version 불일치 시 즉시 실패 + 재시도 → 커넥션을 오래 잡지 않음 → **connection reset 0**

## 해석

### 비관적 락 vs 낙관적 락 트레이드오프

| 관점 | 비관적 락 | 낙관적 락 |
|------|----------|----------|
| p95 | **빠름** (직렬화 1회) | 느림 (재시도 비용) |
| 서버 안정성 | VU 200+ conn_reset | **conn_reset 0** |
| 커넥션 점유 | 길다 (락 대기 동안 점유) | **짧다** (실패 시 즉시 반환) |
| 확장성 | 수평 확장 시 락 경합 심화 | **수평 확장에 유리** |
| 구현 복잡도 | 단순 | 재시도 로직 필요 |

### Phase별 적합성 재평가

| Phase | 규모 | 추천 | 근거 |
|-------|------|------|------|
| 1 (현재) | 500명 | **어느 쪽이든 OK** | 동시 가입 빈도 낮음, p95 차이 체감 안 됨 |
| 2 | 5,000명 | **낙관적 락** | conn_reset 0 + 수평 확장 유리 |
| 3 | 50,000명+ | Redis INCR | 둘 다 DB 경합 한계 |

### yml 전환 전략

```yaml
# Phase 1 — 안전하게 비관적 락으로 시작
triagain:
  crew:
    lock-strategy: PESSIMISTIC

# 동시 가입 이슈 발생 시 → 낙관적 락으로 전환
triagain:
  crew:
    lock-strategy: OPTIMISTIC
```

**재배포 없이 설정만 바꿔서 전략 전환 가능.**

### UX 관점 판단

> **"느려도 응답 받는 것"이 "빨라도 끊기는 것"보다 낫다.**

- 비관적 락: 빠르지만 VU 200+에서 **일부 유저가 아예 응답을 못 받는다** (conn_reset)
- 낙관적 락: 느리지만 **전원이 결과를 받는다** (checks 100%)
- 크루 가입은 "빠른 응답"보다 "확실한 결과 전달"이 중요 — 유저가 가입됐는지 안 됐는지 알아야 함

### 전환 전략

- **Phase 1 (500명)**: 비관적 락으로 시작 — 동시 가입 빈도 낮아 p95 차이 체감 안 됨
- **유저 N명 초과 또는 이벤트 시**: yml 전환으로 낙관적 락 활성화
- **장기 목표**: 런타임에서 트래픽 기반 자동 전환 (특정 동시 요청 수 초과 시 낙관적 락으로)

## 추가 관찰

### checks 100% — 전 구간

| VU | checks | 의미 |
|----|--------|------|
| 50 | 100% (50/50) | 모든 응답이 201 또는 409 |
| 100 | 100% (100/100) | 동일 |
| 200 | 100% (200/200) | 동일 |
| 300 | 100% (300/300) | 동일 — **5xx 0건** |

비관적 락에서도 5xx 0이었고, 낙관적 락에서도 0. 서버 에러율은 전략과 무관하게 0%.

### 재시도 횟수 추정

MAX_RETRY = 3. 크루당 VU 수 = VU / 10 (rush crew 10개).

| VU | 크루당 VU | 성공 가능 최대 | 실제 join_full | 재시도 소진 비율 |
|----|----------|--------------|---------------|----------------|
| 50 | 5 | 3 (retry 3회) | 40 | 0% (5명 중 max 3 retry로 충분) |
| 100 | 10 | 3 | 90 | 0% |
| 200 | 20 | 3 | 190 | 0% |
| 300 | 30 | 3 | 290 | 0% |

모든 실패 VU가 409 (CREW_FULL 또는 CREW_JOIN_CONFLICT)로 정상 처리됨.
CREW_JOIN_CONFLICT (재시도 소진)가 발생했더라도 k6 check에서 409로 잡히므로 join_full에 집계.
