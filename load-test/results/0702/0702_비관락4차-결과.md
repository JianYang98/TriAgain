### 9.1 판정

**vu300의 drop 16건은 TCP 커넥션 수립 계층에서 발생했다. 락·앱·DB 원인은 배제된다.**

결정 근거는 세 관측점의 **삼중 일치(16 = 16 = 16)** — 서로 독립인 측정 경로(k6 클라이언트 / 서버 커널 카운터 / 서버 소켓 스냅샷)가 같은 1~2초 창에서 같은 숫자를 가리켰다:

| 관측점 | 수치 | 시각 | 출처 |
|---|---|---|---|
| k6 `join_dropped` (status 0) | **16건** — 에러 전건 `read: connection reset by peer` (WARN 16줄, 단일 에러 종류) | 09:58:17~19 | 〔측정〕〔측정·터미널〕 |
| `TcpAttemptFails` 델타 (수립 중 커넥션 사망 카운터) | 54→70 = **+16** | 09:58:18 | 〔측정·서버 nstat〕 |
| `SYN-RECV` 소켓 수 (핸드셰이크 미완 소켓) | **16개** (ESTAB=285) | 09:58:17 | 〔측정·서버 ss〕 |

status 0 = HTTP 응답 자체를 못 받음 → 이 16건은 Tomcat/앱에 도달하지 못했다. 같은 창의 `TCPSynRetrans` +73(서버 SYN-ACK 재전송)이 수립 단계에서의 버둥거림을 뒷받침한다.

### 9.2 VU별 TCP 이벤트 카운트 (스트레스 → 흡수 → 실패의 스케일링)

| VU (완료시각) | k6 드롭 | 같은 창 커널 TCP 이벤트 | 결과 |
|---|---|---|---|
| 20 (09:55:52) | **0** | TCPSynRetrans +4 (09:55:50~54) | 전건 완료, connecting max 11.3ms |
| 50 (09:56:17) | **0** | 런 창 내 카운터 무변화 | 전건 완료 |
| 100 (09:57:20) | **0** | TCPSynRetrans **+15** (완료시각과 동일 초) | 재전송으로 전건 흡수 — 드롭 없음 |
| 200 1번째 (09:57:36) | **0** | 무변화 | 전건 완료, p95 846.5ms |
| 200 2번째 (09:57:39) | **0** | **ListenOverflows +141** (ss: acceptQ=101/100, ESTAB=150) | 오버플로 141회 전부 재시도로 흡수 — 드롭 0, 비용은 지연(connecting max 357ms · p95 920.7ms) |
| 300 (09:58:19) | **16** | TcpAttemptFails **+16** · TCPSynRetrans **+73** · ss SYN-RECV=**16** | 16건 reset (status 0), p95 2098.0ms |

- 세션 합계: k6 드롭 **16건(vu300 단독)** / 런 창 기준 커널 TCP 이벤트: SynRetrans +92(4+15+73), ListenOverflows +141, AttemptFails +16.
- 읽는 법: TCP 계층 스트레스는 **vu100부터 커널에 찍히기 시작**(+15)하지만 vu200까지는 재전송이 전부 흡수해 k6에는 지연으로만 나타나고, **vu300에서 처음 흡수 한계를 넘어 16건이 실제 실패**로 떨어졌다.
- 09:42~09:46의 401 런 3건은 드롭 0 (`no conn reset` 체크 20/20 통과) — TCP는 정상, 인증 문제였다. TCP 판정과 무관.

### 9.3 앱 계층 배제 근거

| 항목 | 수치 | 출처 |
|---|---|---|
| 5xx | **0** (전 9런 `join_5xx=0` + Grafana Error Rate "No data") | 〔측정〕〔측정·그래프판독(근사)〕 |
| Tomcat Busy 스레드 피크 | ~150–160 / 한계 200 — 고갈 아님 | 〔측정·그래프판독(근사)〕 |
| Process CPU (런 시간대 09:55~09:59) | 20% 미만 — 포화 아님 | 〔측정·그래프판독(근사)〕 |
| 락 정합성 | 응답 완료 런 전부 `join_success=10` 정확 (정원 초과 0) | 〔측정〕 |
| HikariCP acquire max | ~1s (09:57~09:59 창) | 〔측정·그래프판독(근사)〕 |

- HikariCP acquire ~1s는 **완료된 요청의 지연**(vu300 p95 2098ms)을 설명하는 수치이지 드롭 원인이 아니다 — 풀 대기 중인 요청은 이미 커넥션이 수립되어 앱 안에 들어온 상태라, 실패해도 5xx/타임아웃이지 status 0 리셋이 아니다.
- 드롭 16건은 앱 메트릭(actuator)에 아예 안 보인다 — 앱 도달 전 커널에서 끊겼다는 점과 정합.

### 9.4 층위 소견 — 이번 회차의 특이점

- **accept 큐 오버플로 ≠ 드롭**: vu200 2번째 런에서 ListenOverflows +141이 났지만 k6 드롭 0 — 오버플로는 재시도로 전부 흡수되고 지연만 남았다. 반대로 드롭 16이 난 vu300 창에서는 ListenOverflows **무변화**·acceptQ=51/100(여유). 즉 이번 드롭의 층은 accept 큐가 아니라 **그보다 앞단인 핸드셰이크 수립 단계**(SYN-RECV 16개 사망 → RST)다.
- 3차(07-01)의 결론(SYN 수립 실패층, drop≈SynRetrans, ListenOverflows=0)과 같은 층 판정이며, 4차는 오버플로 이벤트(+141)가 **드롭 없이 공존**했다는 점만 다르다.
- **미확정**: 커널이 그 16개 소켓을 왜 RST로 끊었는지(SYN-ACK 재시도 소진 vs SYN_RECV 상태에서 데이터 수신)는 오늘 로그만으로 확정 불가. 층이 TCP 수립 단계라는 것까지가 수치로 확정되는 범위다.
- 기존 판정과의 정합: t3.micro 커넥션 수립 천장(락 전략 무관, 테스트 박스 한계)이라는 3차까지의 결론과 일치. 락 비교는 드롭이 아닌 완료 요청 p95로만 읽어야 한다는 원칙도 유지.
