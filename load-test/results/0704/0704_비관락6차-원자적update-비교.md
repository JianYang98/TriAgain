## 3. 결정적 대조 — vu500·700에서 두 날의 커널 층이 아예 달랐다 〔파생〕

**6차 vu500·700: 쿠키 발급 0장.** SYN 큐가 한 번도 안 넘쳤다는 뜻이다 (SYN-RECV 피크 147·209 < 256). 대신 SynRetrans 508·790 — 핸드셰이크 패킷이 네트워크에서 유실되고 지수 백오프 재전송(1·2·4·8s)으로 회수됐다. 그 결과 500~700개 연결의 **도착이 11~15초로 펴졌고**(run 11.1s·15.6s = connecting max와 거의 일치), 순간 동시 SYN이 256을 못 넘어 쿠키가 필요 없었다.

**A1 vu500·700: 쿠키 발급 = VU − 256 산수 그대로.** 342/234(vu500), 501(vu700) ≈ 초과분 244·444. run 1.7~3.5s, connecting max < 0.5s — **버스트가 원형 그대로 0.2초 안에 서버에 꽂혔고**, SYN 큐가 즉시 천장(SYN-RECV 피크 236·257 ≈ 256)에 닿아 초과분이 전부 쿠키 폴백으로 넘어갔다. 이 쿠키 경로에서 검증 실패(Failed)가 발생했고, **Failed = 드롭이 런마다 정확히 일치**(3=3, 138=138, 230=230; vu700은 AttemptFails 218=218)한다. 검증 실패한 ACK에 커널이 RST를 쏴서(OutRsts 동반 급증) 클라이언트는 "connection reset by peer"로 즉시 죽었다.

즉 **같은 VU, 같은 서버, 같은 backlog인데 두 날은 서로 다른 커널 층을 지나갔다**:

```
6차  (RTT 41ms): SYN 유실 → 재전송 사다리 → 도착 11~15s로 분산 → SYN 큐 미포화 → 쿠키 0 → 드롭 0, 대신 수립 최대 15.3s
A1   (RTT 25ms): 버스트 원형 도착(<0.5s)       → SYN 큐 즉시 포화  → 쿠키 VU−256장 → 검증실패 → RST → 드롭 138~230, 대신 수립 <0.5s
```

## 4. 그럼 "쿠키 산수"는 왜 6차 vu300에서만 맞았나 〔파생〕

6차에서도 vu300은 쿠키 41장 ≈ 300−256=44 — **A1과 동일한 산수**다. vu400은 10장, vu500·700은 0장으로 급감한다. 즉 6차의 클라이언트 네트워크는 **동시 300발까지는 버스트를 거의 원형으로 전달**했지만, 400발 이상에서는 자체 한계(업링크/NAT)로 패킷을 흘리기 시작해 **네트워크 자신이 트래픽 셰이퍼가 됐다**. A1의 네트워크는 700발까지 원형 전달 — 그래서 A1만 전 구간에서 산수가 성립한다.

## 5. 판정 — 락 전략은 용의선상에서 제외된다 〔분석〕

1. **층이 다르다**: 드롭은 TCP 3-way 핸드셰이크(커널) 단계에서 발생했고, 락 코드는 요청이 Tomcat 워커에 도달한 **이후**에야 실행된다. 드롭된 커넥션은 락 경로를 한 번도 밟지 않았다 (앱 로그 무흔적, 양일 교차검증 완료).
2. **락이 수립층에 역영향을 줄 경로도 없다**: Tomcat NIO의 accept는 acceptor 스레드가 수행하며 워커 점유와 독립(maxConnections 기본 8192 ≫ 700). 응답이 느리든 빠르든 SYN 버스트의 도착 파형은 클라이언트 쪽에서 이미 결정된다.
3. **같은 날·같은 전략끼리도 요동한다**: A1 vu300 ① 3건 → ② 0건 (54초 간격), vu500 ① 138 → ② 230. 전례: 06-23 동일 설정 VU200 6연속 97→93→90→82→9→0 (`INTERVIEW-EPISODE-커널큐-락전략.md`). 드롭 수는 런 단위 확률 변수이지 전략의 함수가 아니다.
4. **역설이지만 데이터가 그렇다**: **A1 날의 네트워크가 "더 좋아서" 드롭이 났다.** 기저 RTT가 절반(41→25ms)인 경로가 버스트를 무손실로 배달했고, 그 온전한 펀치가 t3.micro의 SYN 큐 256 천장을 때렸다. 6차의 무손실은 비관락의 공이 아니라 나쁜 네트워크가 만든 우연한 백프레셔의 결과다.
5. 단정 못 하는 것 (👤 tcpdump 필요): 쿠키 검증 실패의 정밀 서브원인(재전송 교차로 인한 seq 불일치 vs 유효창 만료 vs request sock 조기 폐기). A1 문서 §9.5의 SyncookiesRecv 3.2배 이상치도 동일 — 판정에는 영향 없음(Failed=드롭 1:1은 서브원인과 무관하게 성립).

## 6. 그럼 전략 비교는 어떻게 읽어야 하나 〔분석〕

규약(완료 요청 p95 + 정원 정합성)대로만 읽는다:

- **정합성: 양 전략 만점 동률.** 18런 전부 성공 정확히 10, 초과 0, 5xx 0, (A1은 CR023 충돌도 0).
- **성공(201) 응답 p95**: 6차 154~488ms vs A1 161~404ms (vu50 이상, 6차 vu20 731·A1 vu20 404는 첫 런 워밍업 오염) — **동급**. 두 경로 모두 고VU에서 붕괴하지 않는다.
- **완료 요청 p95의 세션 간 직접 비교는 불가**: 기저 RTT가 다르고(왕복당 ~16ms 가산), 6차 vu400+는 도착 분산으로 파형 자체가 다르다(6차 문서 §9.3의 "비교 금지" 그대로). **A1 vs 비관락의 공정 비교는 같은 세션에서 교차 측정해야만 성립한다** — 이 비교문서가 대신 답할 수 없는 유일한 항목.

## 7. 다음 액션 제안 〔분석〕

1. **동일 세션 A/B 교차 스윕** (비관→조건부→비관→조건부, 네트워크·시간대 고정): 전략 간 완료 p95 공정 비교의 유일한 방법. 드롭이 전략이 아니라 세션을 따라가는지도 이 실험이 최종 확정한다.
2. **accept-count 256 → 1024**: VU700 버스트 전체가 SYN 큐에 수용되면 쿠키층 자체가 소거된다 (이 시리즈 실패 모드의 직접 레버, 07-03 발견의 연장).
3. **런 간격 ≥ 2분**: syncookie 유효창(~2분) 밖으로 벗어나 런 간 잔여 패킷 간섭(A1 §9.5 Recv 3.2배) 제거.
4. **tcpdump 1런** (선택, 블로그용): 쿠키 검증 실패의 서브원인 박제.
5. Prometheus 사후 회수 (A1 창 21:21~21:35, TSDB 보존창 내) 👤.
