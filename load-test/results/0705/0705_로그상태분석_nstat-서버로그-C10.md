## 5. 교차검증 — 드롭의 행방 〔파생〕

**vu500 (k6: 201×10 + 409×265 + 드롭 225 = 500)**

- 서버 도달 = 201 10건(무로그) + CR002 265건 = **275건**. 드롭 225건 = **전원 앱 미도달** (500 − 275 = 225, 오차 0).

**vu700 (k6: 201×10 + 409×454 + 드롭 236 = 700)**

- 서버 도달 = 10 + 458 = **468건**. 앱 미도달 = 700 − 468 = **232건**.
- k6 드롭 236 = 미도달 232 + **"유령 409" 4건** — 서버가 CR002로 처리하고 응답까지 보냈지만 클라이언트는 RST를 받아 status 0으로 계상한 요청. 서버 CR002(458) − k6 409(454) = +4와 정확히 상쇄된다. **드롭 경계가 "수립층"에서 "응답 반환층"까지 4건 침범한 첫 관측.**

**커널 카운터와의 정렬**

| | vu500 | vu700 |
|---|---|---|
| k6 드롭 (RST) | 225 | 236 |
| SynRetrans 창 Δ | 274 | 270 |
| ListenOverflows Δ | 0 | 0 |

드롭 두 런에서만 SynRetrans가 세 자릿수로 폭발 — 시각 정렬은 정확하나 **수량은 1:1이 아니다** (274↔225, 270↔236). C7의 `SyncookiesFailed = OutRsts = 드롭` 같은 등식은 이번 카운터 셋으로는 만들 수 없다.

## 7. 〔분석〕 — 층 분리 결론 (측정값 아님)

1. **accept 큐 층(ListenOverflows)은 용의선상에서 완전 제외.** 1,065초 내내 0 — 6차 상향(accept-count 256) 이후 3세션째 침묵. 드롭 원인은 그보다 앞단(SYN/수립층)이다.

2. **드롭 개시 VU가 300 → 500으로 후퇴했다.** 같은 빠른 네트워크(기저 RTT ~10-15ms)의 C7·C9는 vu300부터 떨어졌는데(40/34건), C10은 vu300·400에서 드롭 0. 9차 §9.3 처방(backlog 상향 실적용 + 재기동)이 이번엔 실행된 것과 정합하는 **수립층 용량 개선 지문**이다. 단, 무엇을 얼마로 바꿨는지 기록이 없어(👤) "무엇의 효과"인지는 미확정.

3. **발현형이 또 새롭다 — "지연 RST".** C7/C9 드롭은 런 초입 0.1~0.3s 내 즉사 볼리(쿠키 검증 실패형), C6은 드롭 0(다초 재전송 사다리형)이었는데, C10 드롭은 **커넥션 수립 성공(connecting avg 104~113ms) → 요청 전송 → ~0.46s(vu500)/~0.68s(vu700) 대기 → RST**다. 같은 초에 서버측 SYN 재전송(SYN-ACK 재전송 포함 카운터)이 +238/+234 폭발. 후보 메커니즘: (a) 최종 ACK 유실·미처리로 서버는 SYN_RECV인 채 클라만 established인 반쪽 커넥션 → 데이터 재전송 끝에 RST, (b) 쿠키 폴백층의 변형 (Syncookies 카운터 부재로 검증 불가), (c) 큐 이동 실패의 다른 경로. (참고: vu500 창에 JVM 첫 Major GC 194ms가 겹치나(Prometheus 회수분) RST는 커널 발신이라 직접 원인 후보에서 제외.) **판별 불가 — 이번 수집이 3종뿐이라서다.** 다음 측정에서 full `nstat -asz`면 C7처럼 등식으로 닫을 수 있다.

4. **드롭은 이번에도 락과 무관.** 드롭 순간 앱로그는 CR002 외 무결(§4) — 비관락 코드는 드롭에 관여할 통로가 없다(6-7-9차 비교 §6 결론 유지). 유일한 신규 뉘앙스는 vu700 유령 409 4건: 앱이 처리를 끝낸 뒤에도 응답이 커널/네트워크 층에서 잘릴 수 있다는 것.

5. **vu50의 +48 재전송 + 균일 216ms connecting**은 드롭 없이 지연으로만 흡수된 소형 이벤트 — C6의 "기다리게 하는 흡수"의 축소판이 빠른 네트워크에서도 순간적으로 나타날 수 있음을 보여준다. 단발 관측이라 해석 확장 금지.
