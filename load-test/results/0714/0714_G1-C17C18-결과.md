# 0714 G1 밤 결과 — C17(G1·off)·C18(G1·on) | 시리즈 최초 비-Serial 세션

> **한 줄 결론**: **Serial식 오염(고VU 런 정중앙 Major 한 방)이 G1에선 아예 발생하지 않는다** — G1 off블록의 자연 활동은 최대 ~30ms young 잔펄스뿐(런내 24회), 게이트는 그중 **이월분만 제거**(24→8회)하고 할당분은 못 지운다. 게이트 pause(G1 Full GC)는 123~231ms로 Serial과 동일 밴드. "게이트로 오염 제거" 가설은 **Serial에서 크게, G1에서 작게** — 오염 단가 자체가 컬렉터에 좌우된다.

> **세션 정체성**: Docker `triagain-loadtest` · 13.125.7.72(t3.micro) · test RDS · **PESSIMISTIC · accept-count 256**(inspect Args, 👤유지 확정) · **G1**(`JAVA_TOOL_OPTIONS=-XX:+UseG1GC` — boot 로그 `Picked up` + 액추에이터 이중증빙, 리빌드 없이 env 주입) · 단일 JVM 기동 07-13 23:35:05 KST · ergonomic heap ~256MB
> **블록 설계**: C17=off 8런 / C18=on 8런, 셔플 20→400→50→300→100→500→200→700, 전 구간 2분 균일 케이던스(블록 전환 포함, 👤확정) · 워밍업 3런(10 on/50 off/200 off, 버림)
> **비교축**: C15(Serial·off)↔**C17(G1·off)** · C16(Serial·on)↔**C18(G1·on)** — 단일 변수 = GC 컬렉터

## 2. 핵심 발견 — G1의 오염 구조는 Serial과 다르다 🏆

### 2-1. off블록 자연 Full/Old GC = 0 (Serial과 정면 대비)

| | off블록 자연 오염 | 형태 | pause |
|---|---|---|---|
| Serial (C15·A9) | **Major 1회씩, 2/2 재현** | 고VU 런 정중앙 한 방 | **192 / 236ms** |
| **G1 (C17)** | **Full/Old 0회** | young 잔펄스 24회 분산 | 관측 max **~30ms** |

C17 8런 내내 `G1 Old Generation` 자연 발화 없음. 힙 축적이 Full로 터지기 전에 young/concurrent가 소화 — **"게이트 없으면 런중 큰 GC가 박힌다"는 Serial 특이 현상**으로 판명.

### 2-2. 게이트의 G1 역할 = 이월 young 제거 (할당분은 불가)

런내 young GC (Evacuation Pause) 장부 — run-log GC 스냅샷 델타:

메커니즘: young은 eden 채움 속도가 결정 — 게이트가 힙을 비워도 런의 할당이 eden을 다시 채우면 터진다(vu400 2↔2). 게이트가 지우는 건 **이전 런들에서 이월된 eden 적재분**(vu500 5→1, vu700 10→3).

### 2-3. 게이트 pause(G1 Full GC) = Serial과 동일 밴드

GcTrigger 로그 9건(w1 166ms + C18 8런 123~231ms), 힙 66~120 → **56MB 상수 리셋**, 런 시작 정렬 **9/9** = System.gc() 카운터 9 정확. G1 Full GC가 더 무겁지 않음(~256MB 힙 기준). Serial 게이트 137~263ms와 겹치는 밴드.

### 해석

1. **PESS 무교란 쌍(무드롭 완료동수: vu20/50/100/200/300) 엇갈림**: on 우세 3(vu20·100·300) vs on 열세 2(vu50·200) — **C15/C16(Serial) 결론 "게이트가 p95 개선한다고 주장 불가"가 G1에서도 재현**.
2. **순서 교락 논의 보완**: 2번째 블록(C18)이 전면 우세 아님 → "나중 블록=성숙으로 항상 이긴다" 단순 가설 기각. A9/A10(COND)의 8/8 우세와 종합하면: **PESS는 락큐가 서버측을 지배해 게이트/성숙 효과가 묻히고, COND는 풀대기가 작아 드러난다** — 전략별 감도 차이. ③효과크기 확정은 여전히 COND on-first 실험 필요.
3. **acquire = PESS 사다리 지문 유지** (C17 p50 132@vu400·165@vu700, 완료부하 단조) — G1로 바뀌어도 락큐 구조 불변.

## 5. 커널 3채널 — 드롭 삼중검증 (미완①종료) 🔬

> **한 줄**: k6 "drop"의 정체를 커널 3채널(nstat·ss·tcpdump)로 확정 — **drop = 클라RST = TcpAttemptFails, 3채널 0오차(727)**. 발생 계층은 **SYN(신쿠키)**이지 accept-queue 아님. GC(게이트)와 인과 단절.

캡처: 박스(en1)에서 nstat 1s 시계열·ss-state·tcpdump 동시, 23:47:40~00:52:30 KST (웜업3+C17 8+C18 8 전 구간 커버).

### 5-1. 드롭 삼중등식 (전 세션 합 = 727)

| 채널 | 지표 | 값 |
|---|---|---|
| k6 클라 | Σ drop (5개 드롭런) | **727** |
| nstat | TcpAttemptFails Δ | **727** |
| tcpdump | RST-In (클라→서버) | **727** |

k6 drop 1건 = 클라가 VU캡 도달 후 서버로 보낸 RST 1건 = 커널 TcpAttemptFails +1. **3채널 완전일치**.

per-run 귀속 (무드롭 11런 = 3채널 전부 0델타, 드롭 5런만 계상):

| 시각 | 런 | k6 drop | nstat AttemptFails Δ | RST-Out(서버) |
|---|---|---|---|---|
| 00:16 | C17 vu400 | 92 | 92 | 78 |
| 00:28 | C17 vu700 | 242 | 242 | 294 |
| 00:33 | C18 vu400 | 25 | 25 | 8 |
| 00:41 | C18 vu500 | 203 | 203 | 98 |
| 00:45 | C18 vu700 | 165 | 165 | 107 |
| **합** | | **727** | **727** | **585** |

- k6 drop = nstat AttemptFails Δ, **16런 전부 1:1**(무드롭 11런도 0=0). 드롭 5런 밖 RST-Out = 0.
- 서버 RST-Out 585 = nstat TcpOutRsts Δ585 = tcpdump RST-Out(win0) 585 — 별개 3채널로 재일치.
- (per-run에서 drop ≠ RST-Out: 클라RST가 drop 정의, 서버RST는 과부하 강제리셋 — 두 방향 별개 카운트)

### 5-2. 드롭 계층 = SYN, accept-queue 아님

| 지표 | 값 | 판독 |
|---|---|---|
| TcpExtListenOverflows | **0** | accept-queue(256) 오버플로 **0** |
| TcpExtTCPReqQFullDrop | **0** | SYN-queue 강제드롭 **0** |
| ss acceptQ 최대사용 | **8 / 256** | 9388샘플 중 9386=0, 백로그 사실상 미사용 |
| TcpExtSyncookiesSent | **2207** | SYN 백로그 초과 → 신쿠키 폴백 발동 |
| TcpExtTCPSynRetrans | **2166** | 클라 SYN 재전송 |
| TcpEstabResets | **1** | 확립연결 리셋 1건뿐 |
| ESTAB 최대동시 | **537** | vu700 피크 |

→ 드롭은 Tomcat accept-count가 아니라 **커널 SYN 백로그·신쿠키 계층**에서 발생. accept-count 256은 전 구간 여유(최대 8/256). = 시리즈 "클라 스케일 = SYN층 지배" **커널 확증**, GC 상태와 무관.

## 6. 게이트 On/Off — 유의미 차이 여부 (사실 종합) 🎯

> 사용자 질문: "G1에서 pre-GC 게이트 on/off, 유의미한 차이 있나?" — 해석 최소, 사실로 답한다. (단일변수 = 게이트, 단 순서 교락 C17먼저·C18나중 미제거)

### 6-1. 게이트가 바꾼 것 (측정된 차이)

| 항목 | off (C17) | on (C18) | 차이 |
|---|---|---|---|
| 런내 young GC(Evac Pause) 횟수 | 24 | 8 | **−67%** |
| Full GC(System.gc()) | 0 | 8 (123~231ms) | 런간 유휴에 8회 주입 |
| 힙 리셋 | 없음 | 66~112MB → 56MB ×8 | 게이트 실동작 확인 |

단, young −67%도 **이월분 한정**: 런 자체 할당분은 못 지움(vu400 off 2 ↔ on 2 동일).

### 6-2. 게이트가 못 바꾼 것 (차이 없음 / 비단조)

| 항목 | off (C17) | on (C18) | 판독 |
|---|---|---|---|
| 자연 Major/Full GC | 0 | 0 | 게이트가 겨냥한 "런중 Major", G1엔 on/off 공히 **0** — 제거 대상 부재 |
| Σ drop | 334 | 393 | on이 오히려 **+59**(비단조). §5에서 SYN층 커널현상으로 확정 → 게이트와 인과 단절 |
| 5xx | 0 | 0 | — |
| 완료 p95 무교란쌍 (§4, vu20/50/100/200/300) | — | — | on 3승(20·100·300) / off 2승(50·200) — **방향 없음** |

### 6-3. 사실 결론

- G1에서 게이트 on/off의 **확정된 유일 효과 = 런내 young GC 횟수 −67%(24→8)**, 그것도 이월분 한정.
- 그 −67%는 **p95·drop·5xx 어디에도 일관된 개선으로 전이되지 않음** (무교란 p95 방향 없음 · drop은 GC와 단절 · 5xx 0=0).
- 게이트 설계 목적(런중 Major GC 선제거)은 **G1에선 on/off 모두 자연 Major 0** → 제거할 대상이 없음.
- ⇒ **G1에서 pre-GC 게이트 on/off의 유의미한 성능 차이는 확인되지 않음** (young GC 카운트 감소 외). on이 추가하는 것은 런간 유휴의 8×(123~231ms) Full GC뿐.
- 유보: 순서 교락 미제거 — 효과크기 최종 확정은 COND on-first 후속 필요(§7).
