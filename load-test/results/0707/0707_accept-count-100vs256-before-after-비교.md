## 0. 한눈에 보는 결론

1. **드롭 개시 VU가 前後로 한 스텝 밀렸다 — 두 전략 공통.**
   - 비관락: 前 vu**200**(33드롭) 개시 → 後 vu**300**(40드롭) 개시
   - 원자적: 前 vu**200**(83드롭) 개시 → 後 vu**300**(37드롭) 개시
   - **vu200이 前엔 드롭(33·83) 때문에 FAIL이었는데, 後엔 드롭 0·checks 100%·PASS로 완전히 정화**됐다. 이게 큐 상향의 가장 깨끗한 이득이다. 대략 "동시 연결 ~100개만큼의 여유"를 산 셈(accept-count +156).

2. **락 정합성은 큐 상향과 무관하게 前後·전 구간 완벽.**
   `success=10`(정원 정확)·`conflict=0`·`5xx=0`이 4개 세션 전 런에서 예외 없이 유지된다. **큐 상향은 연결/커널 층만 건드리고 락 정확성엔 손대지 않는다** — 애초에 드롭은 "워커에 배정되기 전에 튕긴 연결"이라 정원 회계를 깨지 않는다.

3. **병목 층이 이동했다(측정된 범위에서).**
   前(backlog 100)은 **accept 큐 오버플로**가 천장이었다(조건부 前 `ss` Send-Q=100 실측, 드롭을 큐 오버플로로 귀속). 後(256)는 accept 큐가 **한 번도 안 참**(C11·A4 nstat `ListenOverflows=0`, acceptQ `0/256`~순간 87/256) → 남은 드롭(vu300+)은 accept 큐가 아니라 **SYN 수립층**(syncookie 검증 실패 → RST). **큐를 키우자 병목이 accept 큐 → SYN 큐로 올라갔다.**

> **읽기 지침**: 「큐를 100→256으로 키웠더니 드롭이 시작되는 부하가 vu200에서 vu300으로 밀렸고, 정합성은 그대로 완벽했다. 다만 vu300 이상에서는 여전히 드롭이 나는데, 그 원인이 accept 큐(前)에서 SYN 큐(後)로 바뀌었다.」 이 한 줄이 문서 전체 요약이다.

## 4. 공통 발견 〔파생·분석〕

### 4.1 드롭 개시 VU — 두 전략 다 vu200 → vu300 (전략 무관·인프라 층 현상)

| 전략 | 前(100) 개시 VU / 드롭수 | 後(256) 개시 VU / 드롭수 | vu200 전환 |
|---|---|---|---|
| 비관락 | vu200 / 33 | vu300 / 40 | 33드롭·FAIL → **0드롭·PASS** |
| 원자적 | vu200 / 83 | vu300 / 37 | 83드롭·FAIL → **0드롭·PASS** |

- 개시점이 **두 전략에서 똑같이** 한 스텝 밀렸다는 사실이, "드롭은 락/전략이 아니라 **리스너 큐라는 인프라 층**에서 결정된다"는 것을 다시 확인해준다. 큐를 키우면 두 전략 모두 같은 만큼 이득을 본다.

### 4.2 정합성 — 前後·양전략·전 구간 완벽 (큐 상향의 무영향 영역)

- 4개 세션 전 런에서 `success=10 · conflict=0 · 5xx=0`. 드롭이 나든 안 나든, 큐가 100이든 256이든 **정원은 정확히 10명**으로 지켜졌다.
- 검산(회계 일치): 前 비관 vu200 `10+157+33=200`·vu300 `10+193+97=300` / 前 조건부 vu200 `10+107+83=200`·vu300 `10+192+98=300` / 後 C11·A4 각 런 `succ+full+drop=VU` 전부 일치. **드롭은 "정원초과 거부분이 409 대신 연결 리셋으로 샌 회계"**일 뿐, 락이 잘못 입장시킨 게 아니다.

### 4.3 병목 층 이동 — accept 큐 → SYN 층

| | 前 (100) | 後 (256) |
|---|---|---|
| accept 큐 상태 | **오버플로가 천장** — 조건부 前 `ss` Send-Q=100(용량 한계)까지 참, 드롭을 accept 큐 오버플로로 귀속 | **한 번도 안 참** — C11 nstat `ListenOverflows/Drops/BacklogDrop` Δ0 · acceptQ `0/256` 전 구간 (A4는 순간 87/256 포착됐으나 미오버플로) |
| vu300+ 잔여 드롭의 층 | (前엔 vu200부터 accept 층에서 터짐) | **SYN 수립층** — syncookie 발동(vu300~) → 검증 실패분 RST(즉사 볼리). `AttemptFails+EstabResets = dropped` 등식 C11 8/8·A4 4/4 오차 0 |

- 즉 **큐 100→256 상향으로 accept 큐는 병목에서 탈락**했고, 高VU에서 남는 드롭의 원인은 그 **앞단(SYN 큐)**으로 올라갔다. 이래서 256으로 키워도 vu300 이상에선 여전히 드롭이 난다 — accept 큐가 아니라 SYN 큐가 새 천장이기 때문.
- ⚠️ **비관 前(2차)은 `ss`/nstat 계측이 없다.** 위 "前 = accept 큐 오버플로" 직접 실측 근거는 **조건부 前에서만** 나왔고(§4.3 前열), 비관 前의 드롭도 accept 오버플로로 보는 것은 **동일 인프라(backlog 100·같은 t3.micro)에 기댄 추론**이다 — 라벨 구분.

## 5. 캐비앗

1. **cross-session / cross-day** — 前後가 다른 날(前 07-01 / 後 07-06·07-07)·다른 warm 상태. **RDS CPU CreditBalance 미확인 👤**(세션 변동성의 유력 후보). **네트워크(집 와이파이)만 통제**됐다 👤 — 이건 A3/A4 교란을 이 4쌍에서 제거하는 강한 이점이지만, warm/DB 상태 차까지 지우진 못한다.
2. **p95 지표 정의** — 비관 쌍은 前後 동일(`http_req_duration`)이라 그나마 비교 가능하나, **원자적 쌍은 前(scen_d)↔後(완료 201+409)가 달라 p95 결론 금지**. 절대 latency 개선은 이 문서의 주장이 아니다.
3. **생존자 편향** — 드롭이 줄면 느린 요청이 더 많이 완주해 p95가 오를 수 있다(vu300 비관 1220→1441). p95 상승 ≠ 회귀.
4. **前 문서 계측 얕음·스윕 짧음** — 비관 前은 nstat/ss 부재, 前 쌍 모두 vu400+ 없음. 後의 6채널 교차검증과 비대칭.
