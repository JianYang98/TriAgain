# 크루 가입 러시 — 비관락 11차(C11) ↔ 원자적 UPDATE 4차(A4) 비교 · 2026-07-07

> **성격**: 락 전략 비교. **비관락(PESSIMISTIC, C11)** vs **조건부 원자적 UPDATE(CONDITIONAL, A4)** 를, backlog(accept-count)/SYN 큐를 **양쪽 다 256으로 올린 상태**에서, **같은 밤·최대한 맞춘 클라이언트 네트워크**로 측정한 두 세션의 직접 대조 👤.
> **출처 라벨**: 〔측정·k6〕 raw JSON 8런 · 〔측정·Prom〕 acquire 워터마크 · 〔측정·커널〕 nstat/ss · 〔파생〕 원 문서·raw 재계산 · 〔분석〕 해석(§6에 격리).
> **⚠️ p95 재계산**: 두 원 결과서의 p95 정의가 달라서(A4=완료요청만·C11=드롭포함 전체) **양 세션의 raw JSON을 동일 스크립트로 "완료요청(201+409만) p95"로 재집계**했다. 재계산 방식은 A4 결과서 발행값과 8/8 런 **정확 일치**로 검증(§7). 아래 완료 p95는 전부 이 재계산값이다 — **사과 대 사과**.

---

## 0. 한눈에 보는 결론

1. **정합성은 동률·완벽** — 두 전략 모두 8런 전부 `success=10`(정원 정확) · `conflict=0` · `5xx=0`. 락 정합성으로는 우열이 없다. 선택 기준은 성능이다.
2. **완료 p95는 조건부(A4)가 전 구간 우세** — 드롭 없는 통제 구간(vu50/100/200, **양쪽 도달수 동일**)에서 A4가 **21~55% 빠르다**(vu50 −399ms · vu100 −298ms · vu200 −238ms). 드롭 구간(vu300~700)도 vu400 무승부를 빼면 전부 A4 우세. 상태코드 분리로도 거절(409)·승자(201) 양층 모두 A4 우세(§3-1). ⚠️vu50·vu700은 C11 창에 Major GC 겹침 개연(§6.4-5) — 무GC 런(vu100/200/300/500)만으로도 방향 동일.
3. **원인은 DB 풀 경합 — acquire 워터마크 4.5배 차이** — C11(비관) 세션 최대 **1,335ms**(사다리형) vs A4(조건부) **294ms**(무사다리·평탄). 비관락이 `SELECT FOR UPDATE`로 커넥션을 잡고 있는 동안 Hikari 10풀이 직렬화되는 지문. 완료 p95 격차와 방향·크기가 정합. 런별 **acquire 평균도 전 런 C11 열세(2.4~7.8×)**(§4-2) — vu400 무승부의 해명 포함.
4. **드롭·커널층은 전략 무관 노이즈** — 둘 다 vu300부터 즉사 RST(SYN 쿠키 실패)형, t3.micro 커넥션 수립 천장. 총 드롭 C11 592 vs A4 473은 전략 신호가 아니다(런마다 흔들리는 커널 상태).
5. **유령 409 각 1건(vu700)·리소스 여유·단일 기동** — 전부 동률. CPU max 둘 다 ~0.35, 포화 없음.
6. **위치**: 이 쌍은 **정본 통제쌍(07-04 A1↔C7)이 아니다** — 다른 세션·다른 밤 근접(약 4시간 간격)·RDS 크레딧 미확인 👤. 단 **같은 밤 + 네트워크를 맞춘 조건**이라 07-04 결론("무드롭 완료 p95 조건부 우세")을 **강하게 재확인**한다. 전략 우열 정본을 갱신하는 근거로는 쓰지 않고, 보강 표본으로 등재한다(§6.4).

## 4. acquire 워터마크 — 성능 격차의 원인(DB 풀 경합) 〔측정·Prom〕

> **이 지표가 뭔가**: `hikaricp_connections_acquire_seconds_max{job="triagain"}` = 스레드가 **HikariCP 풀에서 커넥션을 받아 오기까지 기다린 시간**의 피크(Micrometer decaying max). **쿼리 실행 시간도, HTTP 응답 시간도 아니다** — DB에 말을 걸기도 전에 "풀에서 커넥션이 날 때까지 기다린 대기 시간"이다. 이게 크면 풀이 막혔다는 뜻.
> **어디서 본 값인가 (출처)**: 로컬 Prometheus(9090)가 EC2 actuator를 5s 주기로 스크레이프 → TSDB 사후 회수분. C11 세션 최대 **1.335115382초(1,335.1ms) @ 00:49:30 KST(vu300 창)**. 원본 파일 `load-test/results/0707/prometheus/hikari_acquire_max.json`, 기록 위치 `prometheus/README.md` L88 · 종합보고서 §4.1. (A4 294ms는 `0706/A4/prometheus/`).
> **읽기 규약**: 워터마크(`*_max`)만 정본 대비, 세션 간 비교만(C7 규약 — 5s 스크레이프는 <1s 버스트를 과소표집).

- **C11(비관): 사다리형** — vu300에서 1,335ms로 치솟음. 비관 시리즈 역대 최고(C7 976 · C10 843). `SELECT FOR UPDATE`가 커넥션을 잡고 있는 동안 Hikari 10풀이 직렬화되는 **비관락 풀지문**.
- **A4(조건부): 무사다리·평탄** — 192~294ms 범위, VU 추세 사다리 없음. 조건부 원자적 UPDATE는 한 번의 왕복으로 커넥션을 즉시 반납(A1 ≤338·A2 ≤383과 동형).
- **acquire 세션 최대 1,335 vs 294 = 4.5배**. 이 격차가 §3 완료 p95 격차(vu50 +399ms 등)의 직접 원인이다 — 방향·크기 정합. 조건부는 **같은 락 정합성을 DB 풀 압력 없이** 산다.

### 4-1. 코드 레벨 메커니즘 — 왜 비관이 풀을 4.5배 막나 〔측정·코드〕

> 실제 구현 확인함. 두 전략 다 **DB가 같은 크루 행의 동시 쓰기를 직렬화**하는 건 동일하다(그래서 정합성도 §2 동률). 차이는 **풀 커넥션을 얼마나 오래 잡고 있느냐**다.

**비관락** — `JoinCrewService.doJoinPessimistic` (JoinCrewService.java:50), 한 트랜잭션 안에서:
1. `findByIdWithLock` = `@Lock(PESSIMISTIC_WRITE)` + `SELECT c ... WHERE c.id=:id` → SQL은 **`SELECT ... FOR UPDATE`** (CrewJpaRepository.java:22) → **행 락 획득**
2. `crew.addMember` — 도메인 정원 검사
3. `save(crew)` → `UPDATE current_members`
4. `saveMember` → `INSERT crew_member`
5. commit → 행 락 해제

→ **행 락이 1→5 전 구간 유지**된다. 같은 크루에 동시 가입한 뒤 요청들은 1번(`SELECT FOR UPDATE`)에서 앞 트랜잭션 commit까지 **블록**되고, 블록된 동안에도 **Hikari 풀 커넥션 1개를 계속 점유**한다. 10풀이 다 물리면 새 요청은 커넥션을 못 받고 **acquire 대기 큐**에 쌓임 → `acquire_max` **1,335ms**.

**조건부 원자적 UPDATE** — `JoinCrewService.doJoinConditional` (JoinCrewService.java:96):
1. `findById` = **락 없는** 일반 SELECT
2. `addMemberSkipCapacityCheck` — 정원 검사 건너뜀
3. `incrementMembersIfNotFull` = **`UPDATE crews SET current_members = current_members + 1 WHERE id=:id AND current_members < max_members`** (CrewJpaRepository.java:46, 네이티브) — **판단(`WHERE current_members < max_members`)과 증가(`SET +1`)를 DB 한 문장에 융합**. 0행 반환 시 `CREW_FULL`
4. `saveMemberAndFlush` → INSERT (중복 가입은 `(crew_id,user_id)` 유니크 제약이 잡아 `CREW_ALREADY_JOINED`)
5. commit

→ 정원 경쟁의 임계 구간이 **3번 UPDATE 문장 하나**로 압축된다. DB는 그 행을 **문장 실행 동안만** 잠그므로 **커넥션 점유 시간이 짧다** → 풀이 막히지 않음 → `acquire_max` **294ms**.

**한 줄 정리**: 비관은 "락을 잡은 채 `SELECT`→정원검사→`UPDATE`→`INSERT`를 왕복" → **커넥션 장기 점유** → 풀 직렬화(acquire 1.3s). 조건부는 "검사+증가를 **원자적 UPDATE 한 방**에 위임" → **커넥션 단기 점유** → 풀 여유(acquire 0.3s). §3의 완료 p95 격차는 이 **풀 대기 차이가 사용자 응답으로 번진 것**이다. 즉 "A4가 직렬화를 안 해서 빠르다"기보다 **"조건부는 직렬화 구간을 DB 행 락 안으로 가두고, 비관은 그 직렬화가 애플리케이션 커넥션 풀까지 번진다"**가 정확한 표현.

### 4-2. acquire 평균 — 워터마크가 아니라 분포 본체로 〔파생, Prom 카운터 재계산, 07-08 추가〕

## 6. 판정과 캐비앗 〔분석〕

### 6.1 판정
- **정합성: 무승부(둘 다 완벽).** 안전성은 전략 선택의 변수가 아니다.
- **성능: 조건부(A4) 우세.** 무드롭 통제 구간 완료 p95 21~55% 우위 + acquire 4.5배 낮음. 사용자 체감 지연·DB 풀 여유 양쪽에서 조건부가 싸다.
- **드롭/커널: 무관.** 인프라(t3.micro) 천장 문제로, 전략 교체로 개선되지 않는다.

### 6.2 이 결과가 말하는 것
같은 락 정합성(정원 10 정확)을 두 전략 다 달성하지만, **비관락은 그 대가로 DB 풀을 직렬화(acquire 1.3s)** 해서 완료 지연을 키운다. 조건부 원자적 UPDATE는 같은 안전성을 **풀 압력 없이(acquire 0.3s)** 사므로 완료 p95가 전 구간 낮다. → **조건부 채택이 성능상 유리**하다는 07-04 결론과 같은 방향.

### 6.3 07-04 정본과의 관계 (재확인)

|---|---|---|
| vu50 완료 p95 | C7 674 → A1 494 (조건부 −180) | C11 726 → A4 327 (조건부 **−399**) |

### 6.4 캐비앗 (왜 정본 통제쌍은 아직 07-04인가)
1. **다른 세션·다른 밤 근접(약 4시간 간격)** — 같은 밤이라 07-04보다 근접하지만, 엄밀한 동시 교차측정은 아니다.
2. **RDS CPU CreditBalance 미확인 👤** — A4 §9.4가 지목한 세션 변동성의 유력 후보. 두 세션의 DB 크레딧 상태가 달랐다면 완료 p95 격차 일부가 그쪽에 귀속될 수 있다. (단 acquire 지문 4.5배는 크레딧으로 뒤집기 어려운 크기.)
3. **vu20 콜드스타트 비대칭** — C11 vu20 완료 p95 2611ms vs A4 431ms. 첫 런 JVM/풀 웜업 페널티가 C11에서 유독 컸다(비교에서 제외). 세션 초기 상태 차의 방증.
4. **네트워크는 "최대한 맞춤"이지 물리적 동일은 아님** 👤 — §7.3에서 connecting 프로파일이 동형임을 실측 확인했으나, 완전 통제는 아니다.
5. **C11 Major GC 2회가 런 창과 겹침 (07-08 재검, 신규)** — `gc_pause` 누적 카운터 재검 결과 C11 창 내 Major GC는 **2회**다: #1 **153ms** @00:43:55~44:00 스크레이프 사이(= **vu50 런 창**, k6 vu50 첫 요청 00:43:54) · #2 **185ms** @00:56:10~15(= **vu700 런 창**, 런 00:56:10~12). 종합보고서·prometheus README의 "창 내 1회(185ms)"는 시리즈 **첫 표본(00:44:00, 누계 1)이 창 내 첫 발생**임을 놓친 과소집계다(Micrometer는 해당 GC가 처음 발생해야 시리즈를 노출 → 첫 표본 시각 ≈ 첫 발생 시각·pause 153ms는 gc_pause_max @00:44:00 실측). A4는 Major GC 1회(159ms)가 20:42:20~25 = vu100↔vu200 **런 사이**로 어느 런과도 비겹침. → **vu50(−399ms)·vu700(−258ms) 격차엔 GC 오염 가능성**: 5s 격자라 초 단위 확정은 불가하고, 겹쳤어도 상한이 GC pause 전량(153/185ms)이므로 잔여 격차(≥−246/−73ms)와 무GC 런(vu100/200/300/500, −238~−339ms)의 방향은 유지된다 — **결론 불변, 단 vu50 "−399·55%↓" 인용 시 이 캐비앗 필수**.

→ 따라서 **전략 우열 정본은 07-04 A1↔C7 통제쌍을 유지**하고, 본 쌍은 **같은 밤·네트워크 맞춤 조건에서의 강한 보강 표본**으로 등재한다.

## 7. 방법론 — p95 재계산과 네트워크 대조 〔파생〕

### 7.1 왜 재계산했나
- A4 결과서 p95 = **완료요청(201+409)만**, C11 결과서 p95 = **드롭 포함 전체 `http_req_duration`**. 정의가 달라 표를 그대로 비교하면 오도된다(C11 결과서 §7.4도 재집계 필요 명시).

## 8. 부록 — 커널·소켓·패킷 상세 대조 (관측 완결성) 〔측정·커널/tcpdump〕

> §5는 "커널층 = 전략 무관 노이즈"를 결론냈다. 이 부록은 그 근거가 된 두 세션의 nstat·ss·tcpdump 채널을 나란히 놓아 **두 세션이 커널 층에서 얼마나 정밀하게 맞물렸는지(관측 완결성)**를 기록한다. 성능 결론(§3·§4)은 바뀌지 않는다 — 이 층엔 전략 신호가 없다. 각 세션 커널 정본: C11 `0707_로그상태분석_nstat-ss-C11.md` · A4 `0706_로그상태분석_nstat-ss-서버로그-A4.md`.

### 8.1 검증 채널 매트릭스 — 두 세션 등식이 동일하게 닫힌다

| 채널 (검증한 등식) | A4 (조건부) | C11 (비관) |
|---|---|---|
| k6 raw: `success+full+dropped=VU` | 8/8 오차 0 | 8/8 오차 0 |
| nstat: `AttemptFails+EstabResets=dropped` | 4/4 오차 0 | 4/4 오차 0 |
| ss: `ESTAB피크=VU−drop+1` | 8/8 오차 0 | 8/8 오차 0 |
| ss: `SYN-RECV 정착값=AttemptFails` | 4/4 (이 채널 최초 발견) | 4/4 (재현) |
| tcpdump: `In RST=dropped`(포트 단위) | — 패킷 미포착 | 4/4 오차 0 |
| tcpdump: `Out RST가 In RST에 선행` | — | 592/592 (예외 0) |
| Micrometer: 유령 409 | 1건 (앱로그 포함 **4중** 관측) | 1건 (앱로그 부재 **3채널** 시간정렬) |

- **핵심**: 두 세션의 드롭 회계 등식이 **똑같이 0오차로 닫힌다** = 드롭은 락 전략보다 아래층(커널 TCP 수립)의 현상. A4가 이 등식(+SYN-RECV census)을 최초로 완성했고, C11이 **tcpdump를 처음 투입**해 패킷 레벨(In/Out RST)로 독립 재확인했다.
- ⚠️ **비대칭**: A4 세션은 tcpdump 미수집, C11 세션은 앱로그(CR002) 부재. 두 세션이 서로의 빈 채널을 메꾸는 상보 관계다.

### 8.2 런별 nstat 델타 대조 (드롭 런 vu300~700) 〔측정·nstat〕

> `A4 → C11` 순. AttemptFails(=영구 드롭)만이 k6 드롭과 1:1 등식을 이룬다.

| VU | AttemptFails (=실드롭) | SyncookiesFailed | ReqQFullDoCookies | OutRsts | EstabResets |
|---|---|---|---|---|---|
| 300 | 37 → 40 | 37 → 40 | 39 → 40 | 37 → 40 | 0 → 0 |
| 400 | 17 → 126 | 17 → 126 | 18 → 127 | 17 → 126 | 0 → 0 |
| 500 | 190 → 213 | 195 → 410 | 212 → 311 | 195 → 410 | 0 → 0 |
| 700 | 228 → 212 | 334 → 290 | 794 → 605 | 334 → 291 | 1 → 1 |

- **AttemptFails**는 두 세션 자릿수 동급(37~40 · 190~213 · 228~212). vu400만 크게 벌어지는데(A4 17 vs C11 126) 이건 전략 차가 아니라 **A4의 vu400 비단조 딥**(그 런의 acceptQ 87/256 순간 흡수, §8.3)이 만든 것 — 그 런의 도착·큐 순간 상태 차다.
- **DoCookies / SyncookiesFailed 잉여**(AttemptFails 초과분)는 드롭으로 전환되지 않고 SYN 재전송이 흡수한 몫 = 노이즈. C11 vu500이 특히 큼(SynFailed 410 vs AttemptFails 213 → 잔차 197) — 이 잔차의 실체가 tcpdump의 "같은 포트에 Out RST 2회 받은 흐름 197건"으로 규명됨(§8.4).

### 8.3 ss 소켓 — ESTAB 등식 · accept 큐 침묵도 차이 〔측정·ss〕

| VU | ESTAB 피크 (=VU−drop+1) | acceptQ 실측 |
|---|---|---|
| 300 | 264 → 261 | 둘 다 `0/256` |
| 400 | 384 → 275 | A4 **순간 87/256** · C11 `0/256` |
| 500 | 311 → 288 | 둘 다 `0/256` |
| 700 | 472 → 488 | A4 **순간 14/256** · C11 `0/256` |

- **ESTAB 피크 = VU−드롭+1**: 두 세션 8/8 오차 0(표는 드롭 런만).
- **accept 큐 침묵도가 갈린다**: C11 = **4중 침묵**(카운터 3종 Δ0 + ss acceptQ 전 구간 `0/256`, 피크 순간 포함) · A4 = **3중 침묵**(카운터) + ss가 vu400·700에 순간 87·14/256 실제 포착. → A4는 큐가 잠깐 쌓였다 드레인, C11은 아예 안 쌓임. **둘 다 오버플로 0**(드롭은 accept층이 아니라 SYN층).
- 이게 §5 결론을 보강한다: "직렬화(비관) → 큐 정체 → 드롭"이 참이라면 **비관(C11)에서 accept 큐가 쌓여야 하는데, 오히려 비관이 큐를 1도 안 채웠다** → 드롭은 앱/락 처리속도와 무관.

### 8.4 발현형 · tcpdump · 유령 409 〔측정〕

- **발현형 = 즉사 볼리, 두 세션 동일**: SynFailed(+동행 OutRsts)가 각 런 첫 1초에 몰리고 AttemptFails가 1~3초 후행(C11 vu300: 00:49:22에 SynFailed 40·SynRecv 109 몰림 → 00:49:23 AttemptFails 38). C10의 "지연 RST(~0.5s)"형과 대비 — C11↔A4는 이 축에서도 동형.
- **tcpdump (C11 단독 관측)**: 드롭 592건 전량 **서버발(Out) RST가 클라발(In) RST에 선행**(In−Out 중앙값 0.88~1.0s, 예외 0) → 서버발 RST가 k6 `connection reset` 오류의 트리거. **Out RST 2회 흐름 = SYN 재전송 3회+ 포트**에서만 발생(vu500 197·vu700 77건) = §8.2 잔차의 정체. 한계: 캡처 필터가 SYN·RST만 잡아(ACK/FIN 없음) 인과 아닌 시간순.
- **유령 409, 둘 다 1건(vu700)·동일 메커니즘**: 수립 완료 후 RST → 서버는 409 생성했으나 소켓 쓰기에서 IOException. A4는 앱로그 CR002+1·커널 EstabResets+1·Micrometer IOException+1·k6 드롭 **4중 확정**, C11은 앱로그 부재로 nstat(EstabResets+1 @00:56:11)·Micrometer(409+IOException @00:56:15)·k6 **3채널 시간정렬**(CR002 초단위 인과는 미확정).
