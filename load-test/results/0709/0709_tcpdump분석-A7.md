## 0. 캡처 개요 & 필터 특성 〔측정〕

- 파일: `tcpdump-203554-A7.pcap`, 총 7,280줄(패킷). 인터페이스 `gif0`.
- 필터: `length 0`, 플래그는 S(SYN) / S.(SYN-ACK) / R(RST) / R.(RST-ACK) 계열만 수집.
- 대상: k6 클라(220.116.188.182) ↔ 서버(15.164.69.243:8080, 내부 172.31.2.204) 8080 트래픽 + 외부 스캔성 IP 2종(§4).
- k6 클라 플래그×방향 전체 합계(v1 7런 합산): **In S 3,057 · Out S. 3,360 · In R 358 · Out R 491**.
- **In R 358 = k6 v1 드롭 358(35+82+241) 정확 일치.** Out R 491 = v1 Out RST 합(35+82+374=491).
- vu500(v2)은 이 캡처 구간(20:36:20~20:46:05 KST) 밖의 별도 재기동(20:54:38) 이후 세션이라 패킷이 존재하지 않는다.

|---|---|---|---|---|---|---|
| 20  | 0   | 0   | 0   | 0   | — | 무드롭 |
| 50  | 0   | 0   | 0   | 0   | — | 무드롭 |
| 100 | 0   | 0   | 0   | 0   | — | 무드롭 |

- **무드롭 4런(20/50/100/200)은 RST 계열 패킷이 0건** — 이 4개 창은 전량 SYN→SYN-ACK로 완결(재전송 여부는 이 facts sheet 범위 밖).
- 드롭 발생 3런(300/400/700)에서 드롭 플로우 = In RST = ISN 2종 플로우 개수가 정확히 일치(35=35=35, 82=82=82, 241=241=241). vu700만 Out RST(374)가 드롭 플로우(241)보다 133 많다 — §3에서 다룬다.
- 첫 RST까지 시간(mean)은 vu300 80ms → vu400 111ms → vu700 406ms로, VU가 커질수록 늘어난다. 세 런 모두 초 단위가 아닌 100ms대~수백ms대 즉사형이며, 지연형(수 초대 흡수)은 관측되지 않았다.

## 2. 드롭 플로우 추적 — ISN₂ 메커니즘 · 첫 RST 〔측정〕

- v1 드롭 플로우는 총 358개(35+82+241)로, **In RST 358·k6 v1 드롭 358과 3자 정확 일치**한다.
- 드롭 메커니즘 = **SYN 쿠키 검증 실패**: 최초 SYN에 대한 서버 SYN-ACK(ISN₁) 이후, 클라이언트 재전송 SYN에 서버가 **다른 ISN(ISN₂)**을 발급하는 패턴이 드롭 플로우 358개 전량에서 관측된다(ISN 2종 플로우 = 드롭 플로우, 오차 0).
- Out RST는 항상 최초 SYN-ACK(ISN₁)의 시퀀스 공간을 종료하는 형태로 발생하고, 최종적으로 클라이언트 측 In RST로 플로우가 종료된다.
- **ISN 2종 발생 ↔ 드롭 여부가 완전 대응**(35/82/241 모두 오차 0) — established 이후 리셋되는 경로(EstabResets)는 관측되지 않는다(§3 nstat 등식과 정합, 유령409 0과도 정합: 3-way handshake가 완성되어 애플리케이션까지 도달했다가 리셋되는 케이스가 없다는 뜻).
- 첫 RST 도달 시간(mean): vu300 80ms · vu400 111ms · vu700 406ms — 즉사형(수백ms 이내 종료), 초 단위로 지연 흡수되는 형태는 이 v1 3런에서 관측되지 않는다.

## 3. 이중/삼중 Out RST = 잉여 〔측정·파생〕

- vu300·vu400: Out RST = In RST = ISN 2종 플로우 = 드롭 플로우(각각 35/35/35/35, 82/82/82/82) — **잉여 0(단일 RST형)**.
- vu700: Out RST **374** = 드롭 플로우 241 + **잉여 133**. 잉여는 하나의 드롭 플로우에서 Out RST가 두 번 이상(이중/삼중) 발생한 결과다.
- vu700 Out RST 374는 nstat SyncookiesFailed 버스트·nstat OutRsts 버스트와 3채널 일치(k6/pcap/nstat 상호 정합) — 잉여 133은 커널 카운터 쪽에서도 동일하게 잡힌다.
- vu500(v2)은 pcap이 없어 이중/삼중 RST 여부를 패킷 레벨로 직접 확인할 수 없다. nstat_v2 기준 OutRst = 220 = drop 220으로, 잉여 0(단일 RST형)에 해당하는 수치이나 **패킷으로 검증된 것은 아니다** — nstat_v2가 정본이며 이 문서는 참고만 한다.

## 4. 비-k6 트래픽 〔측정〕

- 외부 스캔성 IP 2종: **94.154.43.230**, **188.166.40.87** — 각 SYN 1발 + 서버 SYN-ACK 6회 응답, 2개 IP 합산 총 **14패킷**. k6 클라 IP(220.116.188.182)와 무관한 배경 트래픽이다.
- v1 7런 창 밖/사이 시간대에 8080 포트로 유입된 것으로 관측되며, 드롭 등식(§1·§3)에는 포함되지 않는다.

- **드롭 등식 8/8 오차 0**(EstabResets 전 런 0 → 유령409 0과 정합. 4런 무드롭 포함하면 8/8).
- v1 3런(300/400/700)은 pcap 드롭플로우=In RST=ISN 2종=k6 드롭이 정확히 일치(35/82/241). vu700만 Out RST(374)가 나머지 채널보다 133 많다(§3 잉여).
- vu500은 **패킷 채널(드롭플로우·In RST·ISN 2종) 전부 pcap 부재로 공란** — nstat_v2 등식(220=220)과 OutRst(220)·ss_v2 SYN-RECV 피크(224)로만 대체 확인되며, 이 표에서 vu500 행은 참고용이지 pcap 검증이 아니다.
- ListenOverflows는 v1·vu500 전 런에서 0(accept 큐 자체 오버플로는 없음, 단 acceptQ 실사용은 있었다 — 로그상태분석 정본 참조).

## 6. 관측이 시사하는 것 / 확정하지 않는 것 〔분석 — 사실 아님〕

- ACK 패킷이 캡처 필터에서 빠져 있어(S/S./R/R.만 수집) 3-way handshake 완성 여부를 패킷으로 직접 확인할 수 없다 — ISN 2종·Out RST·In RST 패턴으로부터의 추론일 뿐, 확정 아님.
- **vu500은 패킷 레벨 관측이 전혀 없다.** ISN₂ 패턴, 첫 RST 분포, 이중/삼중 RST 여부 등 이 문서의 핵심 메커니즘이 vu500에도 동일하게 적용되는지는 확인 불가 — nstat_v2·prometheus-vu500-v2가 대체 정본이다.
- 드롭이 vu300부터 시작되는 원인(SYN 큐 크기, backlog, accept-count 등 어느 축이 결정적인지)은 이 pcap 단독으로 특정할 수 없다.
- vu700에서만 이중/삼중 Out RST(잉여 133)가 관측된 이유(다른 VU에는 없음)의 근본 메커니즘은 미확정.
- **전략(조건부 UPDATE/비관적 락) 라벨은 이 문서에서 확정하지 않는다** — A7 세션 전체가 👤 미확정 상태이며, 이 tcpdump 분석 결과를 전략 판단의 근거로 사용하지 않는다.
- accept-count 설정값(ss 관측은 `/256`)도 이 문서로는 확정하지 않는다.
