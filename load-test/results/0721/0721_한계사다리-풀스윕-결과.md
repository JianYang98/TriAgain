# 한계 사다리 + HikariCP 풀 스윕 결과 — 용량·병목 규명 (2026-07-21)

> 실험 질문: **이 서버 구성이 감당하는 최대 처리율은 얼마이고, 그 벽의 정체는 무엇인가?**
> 6런 본측정(`0721_TPS-6런-결과.md`)이 "500/s까지 완주·한계 미도달"로 끝나 같은 날 👤승인으로 이어 실행.

## 1. 한계 탐색 사다리 (CONDITIONAL × A, const 60s/스텝, 기동 #9)

> 6런에서 "500/s까지 완주·한계 미도달"이었으므로, 채택 전략(CONDITIONAL)으로 천장을 탐색.
> 스텝 간 리셋, 동일 기동(재기동 1회 + 워밍업), VU는 리틀의 법칙 여유 2배(300/600 · 400/800 · 500/1000).

- 달성 rate = 전체 처리 TPS (status0 드롭 0이라 동일 — k6가 응답받은 만큼이 곧 서버 처리량)

서버측 (3스텝 공통): CPU max ~90% | Tomcat busy **200/200 만석** | Hikari pending **~189** (구조 상한: 스레드 200 − 커넥션 10 점유)

**판정**:
- **무릎(knee) = 500~600/s 사이.** 500/s 유지는 p95 176ms·드롭 0으로 소화, 600/s에서 p95 1.68s(10배)·드롭 9.6%로 급전환.
- **실용 한계(지연 SLO 관점) ≈ ~500/s** / **절대 처리 천장 ≈ ~680/s** (동시성 1,000 압력·지연 2초대 감수 시).
  달성 rate는 VU 상한 하의 값이나, 상한 도달 시 달성률은 서버 응답 지연이 결정하므로 서버 용량을 반영한다.
- **병목 체인**: Hikari 풀(10) 깔때기 → Tomcat 스레드(200) 만석 → CPU ~90%. 커널 아님 (오버플로 r800 45건뿐, SYN 재전송으로 회복·요청 손실 0).
- **실패 모드**: 5xx 0·연결 실패 0·dup 0 (3스텝 전부) — 죽지 않고 **순수 큐잉(지연 폭주)으로 우아하게 포화**.
- 최종 문장: *"t3.micro + micro RDS + CONDITIONAL 구성의 크루 참여 처리율은 지연 정상 범위에서 ~500/s가 한계이며,
  그 위로는 처리량이 사다리꼴로 완만히 늘지만(534→625→677/s) p95가 1.7~2.1초로 폭주한다. 병목은 커넥션 풀·스레드 직렬화."*

- ⚠️ nstat 로그 판독 주의: `nstat_*.log`의 값은 초당 증분이 아니라 **감시 시작 이후 누적값의 재출력**이다(사다리 r800=45 반복 출력으로 교차 확인). 런당 실제 발생 건수 = 로그 내 최대값.

raw `prom_ladder_*`·`prom_poolsweep_*`에서 기동 epoch 경계로 구간 분리 후 max 산출):

| 구간 (기동) | CPU max (프로세스) | Hikari active max | **Hikari pending max** | **Tomcat busy max** | acquire max |
|---|---|---|---|---|---|
| 풀 10 = §1 사다리 (#9) | 90.2% | 10 (상한) | **189** | **200 (만석)** | **3.27s** |
| 풀 20 (#10) | 92.0% | 20 (상한) | 179 | 200 (만석) | 2.16s |
| 풀 30 (#11) | 90.6% | 30 (상한) | 173 | 200 (만석) | 2.53s |

- 세 구간 모두 **active = 풀 상한 도달**(커넥션 전부 사용) + busy 200 만석 — pending ≈ 200−active(스레드 수 구조 상한). 5xx·dup 전 스텝 0.
- 호스트 전체 CPU(system) max는 98.9~99.1% (풀 20/30 구간) — "벽 = CPU"의 직접 증빙.

**판정: 가설 B 확정 + α — 풀 확대는 이동이 아니라 역효과.**
- 처리량이 풀 크기에 **단조 감소** (1000/s 기준 677 → 624 → 577, −15%). 커넥션을 다 쓰면서도 느려짐
  = DB 동시 쿼리 증가가 포화된 CPU(2 vCPU)·micro RDS에서 문맥전환·경합 비용만 키움.
- pending 189는 병목의 "원인"이 아니라 "증상"이었음 — 진짜 벽은 CPU. **기본 풀 10이 이 하드웨어의 사실상 최적점.**
- **acquire 대기 실측이 "이동"을 직접 증명**: `hikaricp_connections_acquire_seconds_max` 피크가
  풀 10=3.27s → 20=2.16s → 30=2.53s — 풀 확대로 **획득 대기(보이는 큐)는 줄었는데 처리량도 같이 줄었다**.
  대기가 사라진 게 아니라 풀 앞 대기줄 → 쿼리 실행 시간 안쪽으로 이사한 것 (포화 CPU에서 쿼리 자체가 느려짐).
- 교훈: "대기열이 보이는 곳"과 "병목인 곳"은 다르다. 풀 확대는 공짜가 아니며, CPU 포화 상태에선 동시성 추가가 처리량을 깎는다.
- ⚠️ 순서 캐비앗: 풀 10(15:09)→20(16:03)→30(16:11) 순차 실행이라 시간 교락 가능성은 있으나,
  단조 추세 + 3레이트 전부 일관이라 노이즈로 설명 안 됨.


## 3. 종합 결론

- **실용 한계 ≈ 500/s** (지연 정상 범위) / 절대 천장 ≈ 680/s (풀 10, 지연 2s대 감수)
- **벽의 정체 = CPU** (2 vCPU 포화 ~90%). 풀 확대는 acquire 대기(보이는 큐)를 줄이지만 처리량을 깎는다 — 병목은 사라지지 않고 쿼리 실행 안쪽으로 이동
- **기본 풀 10 유지가 실측 최적** — prod 설정 변경 불필요
- 실패 모드는 전 구간 우아한 포화 (5xx 0·연결 실패 0·dup 0)
