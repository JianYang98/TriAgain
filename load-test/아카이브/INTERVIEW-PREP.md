# 부하테스트 면접 답변 준비

> 예상 질문: "부하테스트 경험이 있으신가요?", "성능 테스트를 어떻게 진행하셨나요?"

> 최종 갱신: 2026-04-20

## 30초 — 엘리베이터 피치

사이드 프로젝트 TriAgain 백엔드를 EC2 t3.micro 단일 노드에서 k6로 8일간 부하테스트했습니다. 읽기 912 req/s, 쓰기 490 TPS를 실측했고, 동시 사용자 250명까지 서버 에러율 0%를 확인했습니다. 비관적 락으로 300명 동시 가입에서도 정원 초과 0건 — 데이터 정합성 100%를 증명했고요. 가장 큰 배움은 k6의 기본 판정 기준이 비즈니스 거절(409)을 서버 장애로 오판하는 문제를 발견하고, 판정 기준 자체를 재정의해야 한다는 것이었습니다.

---

## 2분 — STAR 구조

### Situation

습관 형성 앱 TriAgain을 개발하고 있었습니다. Phase 1 목표가 유저 500명, 피크 50 TPS인데, 실제로 서버가 얼마나 버티는지 정량적 근거가 없었습니다. Spring Boot + PostgreSQL, EC2 t3.micro 단일 노드 환경입니다.

### Task

"이 서버가 실제로 얼마나 버티는가"를 숫자로 증명하고, 병목이 어디인지 찾아서 Phase 2 스케일업 전략의 근거를 마련하는 것이 목표였습니다.

### Action

k6 + Prometheus + Grafana 모니터링 체인을 구축하고, 8일에 걸쳐 7종 시나리오를 측정했습니다.

그 과정에서 두 가지 핵심 발견이 있었습니다.

**첫째, 측정 도구가 거짓말을 했습니다.** k6가 에러율 6.82%로 FAIL을 찍었는데, 서버 로그에는 5xx가 하나도 없었습니다. 원인을 파보니 k6의 `http_req_failed`가 409 Conflict — 하루에 한 번만 인증할 수 있다는 비즈니스 규칙에 따른 정상 거절 — 을 서버 에러로 카운트하고 있었습니다. `check()`로 "201 또는 409는 성공"이라고 직접 정의하고, `checks_failed`로 판정 기준을 바꾸니 에러율 0%였습니다. 같은 데이터인데 판정 기준만 바뀌었을 뿐입니다.

**둘째, TPS 920이라는 숫자의 실체를 발견했습니다.** 혼합 부하에서 `http_reqs/s = 920`이 나왔는데, 엔드포인트를 분해해보니 99.7%가 GET 읽기였고 실제 DB INSERT는 0.41/s뿐이었습니다. 쓰기 전용 시나리오를 따로 만들어서 측정하니 진짜 쓰기 TPS는 490이었습니다.

### Result

읽기 912 req/s, 쓰기 490 TPS를 확정했습니다. Phase 1 목표 대비 읽기 18배, 쓰기 10배 여유가 있다는 걸 증명했고요. 동시성 테스트에서는 SELECT FOR UPDATE 비관적 락으로 300명이 동시에 달려들어도 정원 10명을 정확히 지키는 걸 확인했습니다. 병목은 CPU가 아니라 GC Pause(4.6초)와 HikariCP 커넥션 점유라는 것도 특정했고, 튜닝 우선순위를 GC → Pool → 인스턴스 순으로 확립했습니다.

## 5분 — 기술 깊이 (후속 질문에 맞춰 전개)

> 2분 답변 후, 면접관 질문 방향에 따라 아래 3개 중 선택해서 깊이 들어감

### (A) 방법론 — "판정 기준을 어떻게 재정의했나요?"

k6에는 `http_req_failed`라는 기본 메트릭이 있는데, HTTP status 400 이상은 전부 실패로 셉니다. 문제는 409 Conflict가 저희 서비스에서는 정상 비즈니스 거절이라는 점입니다. "같은 유저가 같은 날 같은 크루에 두 번 인증" — DB UNIQUE 제약이 걸려있고, 서비스 레이어에서 먼저 검사해서 409를 돌려줍니다.

50명 유저가 반복 호출하는 피크 시나리오에서, 첫 50건은 201 Created, 나머지 2,000건은 전부 409입니다. k6 입장에서는 에러율 6.82%. 서버 입장에서는 에러 0건.

해결은 두 단계였습니다. 먼저 `check()`로 "201 또는 409는 성공"이라고 선언했습니다. 그리고 threshold를 기본 `http_req_failed`에서 `checks: ['rate>0.99']`로 바꿨습니다. 추가로 `Counter`를 둬서 201(생성)과 409(중복)를 따로 집계해 리포트에서 한눈에 보이게 했고요.

교훈은 **"도구 기본값을 맹신하지 말 것, 우리 도메인에서 실패가 뭔지 먼저 정의할 것"**입니다.

### (B) 병목 분석 — "병목이 어디였나요?"

Grafana에서 쓰기 부하 때 세 가지 메트릭을 봤습니다.

- HikariCP Pending max 140 — pool=10인데 대기가 140까지 쌓임
- GC Pause max 4.6초 — Stop-the-World 동안 커넥션을 쥐고 있음
- CPU 85% — 의외로 CPU는 읽기 때(100%)보다 여유

쓰기 1건이 SELECT 4-5번 + INSERT 1번 + UPDATE 1번 = 6-7 DB 오퍼레이션이라 커넥션 점유 시간이 깁니다. 여기에 GC Pause가 겹치면 커넥션을 쥔 채 멈추니까 뒤의 요청들이 Pending으로 쌓이는 구조입니다.

그래서 튜닝 우선순위를 이렇게 잡았습니다:
1. **GC 튜닝** — MaxGCPauseMillis=200 설정으로 STW 시간 줄이기 (가장 명백한 병목)
2. **Pool 확장** — GC 튜닝 후에도 Pending이 높으면 pool 20으로
3. **인스턴스** — CPU가 여전히 100%이면 t3.small로

재미있는 건 HikariCP timeout이 Day 1~8 전 구간에서 0이었다는 점입니다. "DB 커넥션 풀부터 늘리자"가 흔한 접근인데, 실제로는 pool 자체가 병목이 아니라 GC가 병목이었습니다.

### (C) 동시성 — "정합성은 어떻게 보장했나요?"

크루 정원 10명인 상태에서, 50명~300명이 동시에 가입 요청을 보내는 시나리오를 만들었습니다.

`SELECT FOR UPDATE`로 크루 row를 잠그고, 현재 멤버 수를 세고, 정원 미달이면 INSERT하는 구조입니다. 결과는 전 구간에서 `join_success = 10` 정확히 일치. 300명이 동시에 달려들어도 정원 초과 0건이었습니다.

다만 트레이드오프가 있었습니다. p95가 VU당 약 2ms씩 선형 증가합니다. 직렬화 비용이죠. VU 200부터는 Tomcat connection reset이 발생했는데, 이건 락 경합이 아니라 서버 동시 연결 수 한계였습니다.

그래서 Phase별 전환 전략을 세웠고, **실제로 낙관적 락을 구현해서 Before/After를 측정했습니다.**

비관적 락은 빠르지만 VU 200부터 connection reset이 발생합니다 — 일부 유저가 아예 응답을 못 받는 문제입니다. 낙관적 락은 p95가 2~3배 느리지만, VU 300에서도 connection reset 0입니다. 전원이 결과를 받습니다.

UX 관점에서 판단했습니다: **"느려도 응답 받는 것"이 "빨라도 끊기는 것"보다 낫다.** 크루 가입은 유저가 가입됐는지 안 됐는지를 반드시 알아야 하는 행위니까요.

그래서 yml 설정 한 줄로 비관적/낙관적을 전환할 수 있게 설계했습니다. Phase 1은 비관적 락으로 시작하되, 유저가 늘거나 이벤트 트래픽이 몰릴 때 낙관적으로 전환합니다. 장기적으로는 런타임에서 동시 요청 수가 일정 임계치를 넘으면 자동 전환하는 것을 고려하고 있습니다.

보너스로 스케줄러 중복 실행 문제도 발견했습니다. `fixedRate`가 처리 시간보다 긴 경우 즉시 재실행되는데, `@Version`이 없어서 같은 row를 두 번 UPDATE해도 예외가 안 납니다. 현재는 멱등 UPDATE라 무해하지만, 알림 같은 부수 효과가 붙으면 버그가 됩니다. `fixedDelay`로 1줄 변경하면 해결되는 문제입니다.

## 꼬리 질문 대비 카드

### "왜 k6를 선택했나요?"

코드로 시나리오를 정의할 수 있어서입니다. JavaScript 기반이라 시나리오 A(읽기), B(쓰기), D(동시성)를 모듈로 분리하고 조합할 수 있었고, `Counter`, `Trend` 같은 커스텀 메트릭을 코드 안에서 선언할 수 있어서 비즈니스 메트릭(verify_created, verify_duplicate)을 바로 집계했습니다. CLI 기반이라 EC2에서 바로 돌릴 수 있는 것도 장점이었고요.

### "실 서비스 트래픽과 차이점은?"

가장 큰 차이는 트래픽 패턴입니다. 테스트는 동일 API 반복 호출이지만, 실제는 다양한 엔드포인트가 섞입니다. 다만 "마감 직전 인증 몰림" 시나리오가 가장 현실적인 피크 패턴이라고 판단했고, 여기서 얻은 수치가 가장 의미 있었습니다. 읽기/쓰기 비율도 90:10(평상시), 40:60(마감 피크) 두 가지로 나눠서 측정했습니다.

### "다시 한다면 뭘 바꾸겠나요?"

세 가지입니다.

1. **판정 기준 + 환경 검증을 Day 0에 확립하겠습니다.** Day 1~2는 데이터 오염 해결과 판정 기준 재정의에 소비했고, Day 6에서야 인스턴스 타입이 t2가 아니라 t3이라는 걸 알았습니다. 측정 전에 "실패의 정의"와 "환경 실측"을 먼저 하면 하루는 아꼈을 겁니다.

2. **읽기/쓰기 분리 측정을 초반부터 했겠습니다.** "TPS 920"을 한동안 전체 처리량으로 보고했는데, 분해해보니 99.7%가 읽기였습니다. Day 7에서야 쓰기 전용 시나리오를 만들었는데, 이걸 Day 1에 했으면 더 일찍 정확한 수치를 잡았을 겁니다.

3. **GC 로그를 처음부터 켜놨겠습니다.** Grafana로 Pause max만 관찰했는데, GC 로그가 있었으면 Pause 분포와 원인을 바로 분석할 수 있었습니다.
