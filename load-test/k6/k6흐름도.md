# k6 부하테스트 흐름도 (직접 돌려보기용)

> 목적: 내가(사용자) k6 스크립트를 **직접 읽고 직접 돌릴 수 있게** 하는 학습 문서.
> 기준: 이 레포(`triagain-back/load-test/k6/`)의 실제 스크립트.

---

## 1. k6가 뭔가

k6 = **부하 테스트 도구**. "여러 명이 동시에 우리 API를 때렸을 때 서버가 버티는가"를 측정한다.

기억할 3가지:
- **시나리오를 JavaScript로 쓴다.** (그래서 `.js` 파일들이 있음)
- **가상 유저(VU, Virtual User)** 를 N명 만들어 동시에 HTTP 요청을 쏜다.
- 끝나면 **p95 응답시간, 실패율, 처리량(RPS)** 같은 숫자를 뱉는다.

실행은 한 줄. `node`가 아니라 `k6` 바이너리로 돌린다:

```bash
k6 run smoke.js
```

> 설치 확인: `k6 version` (없으면 mac은 `brew install k6`)

## 2. k6 스크립트의 "계약" — 모든 파일이 이 모양

제일 단순한 `smoke.js`로 골격을 본다. **모든 k6 스크립트는 이 3조각으로 되어 있다:**

```javascript
// k6/smoke.js
export const options = {           // ① 부하를 "얼마나" 줄지
    vus: 2,                        //    가상 유저 2명
    duration: '30s',               //    30초 동안
    thresholds: {                  //    합격/불합격 기준
        http_req_duration: ['p(95)<500'],   // 95%가 500ms 안에 끝나야 함
        http_req_failed:   ['rate<0.05'],   // 실패율 5% 미만
    },
};

export default function () {       // ② VU 한 명이 "무엇을" 반복할지
    crewHome();                    //    → 크루 홈 GET 호출
}

export { handleSummary } from './lib/report.js';  // ③ 결과를 "어떻게" 저장할지
```

| 조각 | 역할 | 비유 |
|------|------|------|
| `options` | 부하 양 + 합격 기준 | "2명이 30초 뛰어라, 95%는 0.5초 안에 들어와야 합격" |
| `export default function` | VU가 반복 실행하는 본문(iteration) | 유저 한 명의 행동 대본 |
| `handleSummary` | 끝나고 리포트 파일 생성 | 성적표 출력 |

### 핵심 개념 4개

- **VU (Virtual User)**: 동시 사용자 수. `vus: 2` = 2명이 병렬로.
- **Iteration(반복)**: VU가 `default function`을 한 번 도는 것. 시간 동안 계속 반복.
- **Check**: "응답이 200이냐?" 같은 참/거짓 검사. 실패해도 테스트는 안 멈추고 통계만 쌓임.
- **Threshold(임계값)**: 합격선. 못 넘으면 k6가 **exit code 1**(실패)로 끝남 → CI에서 사용 가능.

## 3. 이 레포 구조 — 왜 파일이 여러 개인가

**"진입 스크립트"** 와 **"공용 라이브러리"** 로 나뉘어 있다. 이게 핵심 설계다.

```
k6/
├── smoke.js          ← 진입점: "부하를 얼마나" 만 정의 (options)
├── load-normal.js    ← 진입점: 평상시 부하 (읽기90:쓰기10)
├── crew-rush.js      ← 진입점: 정원 경합 동시성 테스트
├── dup-join.js       ← 진입점: 중복 가입 동시성 테스트
├── stress.js / saturation.js ...
└── lib/              ← 공용 부품 (진입점들이 가져다 씀)
    ├── config.js     ← BASE_URL, 토큰 로딩, 유저↔크루 매핑
    ├── scenarios.js  ← 실제 행동 함수 (crewHome, writeScenario, crewRush...)
    ├── metrics.js    ← 커스텀 측정 카운터 정의
    └── report.js     ← 결과 HTML/JSON 저장
```

**왜 나눴나?** 행동 로직(`crewRush`)은 한 군데(`scenarios.js`)에만 두고, 진입 스크립트들은 "VU 몇 명, 몇 초" 같은 **부하 모양만** 다르게 정의한다. 그래서 `crew-rush.js`가 14줄밖에 안 된다 — 실제 일은 전부 `lib/`가 한다.

흐름:
```
crew-rush.js ──import──> scenarios.js(crewRush) ──import──> config.js(토큰·URL) + metrics.js(카운터)
```

## 4. crew-rush.js 한 줄씩 — "시나리오 D"

**목적: 정원 10명짜리 크루에 50명이 동시에 가입 버튼을 누르면, 정확히 10명만 성공하고 40명은 "정원 초과" 되는가?** (동시성/락 검증)

```javascript
// k6/crew-rush.js
import { crewRush } from './lib/scenarios.js';   // 실제 행동은 lib에서 가져옴

const vus = parseInt(__ENV.TARGET_VUS || '50');         // ← --env TARGET_VUS 로 조절. 기본 50
const maxMembers = parseInt(__ENV.MAX_MEMBERS || '10'); // ← 크루 정원. 기본 10
const expectedFull = vus - maxMembers;                  // ← 50-10 = 40명은 정원초과 나야 정상
```

`__ENV.XXX` = **실행할 때 넘기는 환경변수**. `k6 run --env TARGET_VUS=100 ...` 하면 `vus`가 100이 된다. **코드 안 고치고 부하를 바꾸는 방법.**

```javascript
export const options = {
    scenarios: {
        rush: {
            executor: 'per-vu-iterations',  // ← 핵심! 아래 표
            exec: 'rushExec',               // 이 시나리오가 부를 함수 이름
            vus: vus,                       // 50명
            iterations: 1,                  // 한 명당 딱 1번만 (가입은 1번이면 됨)
            maxDuration: '30s',
        },
    },
```

**`executor`가 k6에서 제일 중요한 개념.** "VU들을 어떻게 굴릴까"의 정책이다:

| executor | 의미 | 어디 쓰나 |
|----------|------|----------|
| `per-vu-iterations` | VU마다 정해진 횟수만 실행하고 끝 | **crew-rush**: 50명이 각자 1번씩 가입 → 동시 경합 재현 |
| `constant-vus` | N명이 정해진 시간 동안 계속 반복 | 고정 부하 |
| `ramping-vus` | VU를 단계적으로 늘렸다 줄임 (10→50→100) | 평상시 부하 곡선 |
| `ramping-arrival-rate` | "초당 요청 수"를 목표로 맞춤 (VU 자동 조절) | 쓰기 부하 RPS 제어 |

crew-rush가 `per-vu-iterations` + `iterations: 1`인 이유: **"50명이 거의 동시에 딱 한 방씩 가입을 쏜다"** 를 만들려는 것. 그래야 `SELECT FOR UPDATE` 락 경합이 진짜로 일어난다.

```javascript
    thresholds: {
        http_req_duration: ['p(95)<1000'],
        join_success: [`count==${maxMembers}`],   // ← 성공이 정확히 10이어야 합격
        join_full:    [`count==${expectedFull}`], // ← 정원초과가 정확히 40이어야 합격
    },
};
```

여기가 멋진 부분. 단순히 "빠른가"가 아니라 **"정원이 정확히 지켜졌는가"를 합격 조건으로 박아놨다.** 11명이 가입되면(락 버그) `join_success==10`이 깨져서 테스트가 빨갛게 실패한다.

```javascript
export function rushExec() {   // options의 exec: 'rushExec'가 이걸 가리킴
    crewRush();                // 실제 일은 scenarios.js의 crewRush()
}

export { handleSummary } from './lib/report.js';  // 리포트 저장
```

## 5. scenarios.js의 crewRush() — 실제로 요청을 쏘는 곳

`crew-rush.js`는 "설정"이고, **진짜 HTTP 요청은 여기서** 일어난다.

```javascript
// k6/lib/scenarios.js
export function crewRush() {
    const params = authHeaders(__VU);   // ← 이 VU의 인증 토큰을 헤더에 담음
    const rushCrewId = `loadtest-rush-crew-${(__ITER % RUSH_CREW_COUNT) + 1}`;

    // 진짜 요청: POST /crews/{crewId}/join
    const res = http.post(`${BASE_URL}/crews/${rushCrewId}/join`, null, params);
    scenarioDDuration.add(res.timings.duration);  // 응답시간을 커스텀 지표에 기록

    // 응답을 status/에러코드별로 분류해서 카운트
    if (res.status === 201) {
        joinSuccess.add(1);                       // 가입 성공
    } else if (res.status === 409) {
        const code = errorCode(res);
        if (code === 'CR004')      joinDup.add(1);       // 중복가입
        else if (code === 'CR023') joinConflict.add(1);  // 낙관락 재시도 소진
        else                       joinFull.add(1);      // 정원초과(CR002)
    } else if (res.status >= 500) {
        joinError5xx.add(1);                      // 서버 에러
    } else if (res.status === 0) {
        joinDropped.add(1);                       // 연결 끊김(status 0)
    }

    check(res, { 'D: join or full': (r) => r.status === 201 || r.status === 409 });
}
```

알아둘 것:

- **`__VU`** = 현재 가상 유저 번호(1, 2, 3...). **`__ITER`** = 현재 반복 횟수. k6가 자동으로 넣어주는 전역 변수.
- **`authHeaders(__VU)`** (config.js): VU 번호로 `tokens.csv`에서 토큰을 골라 `Bearer xxx` 헤더를 만든다 → VU마다 다른 유저로 가입 시도.
- **응답 분류가 정교하다.** "성공/실패"가 아니라 HTTP status + 백엔드 에러코드(CR002/CR004/CR023)까지 쪼개서 센다. 이게 A/B/C 락 전략 비교의 핵심 데이터였다 (런북 참고).
- `metrics.js`의 `joinSuccess` 같은 건 **카운터**. `.add(1)` 하면 1 증가. 끝나면 리포트에 `join_success: 10` 이렇게 찍힌다.

### scenarios.js에 있는 다른 시나리오 함수

| 함수 | 시나리오 | 하는 일 |
|------|----------|---------|
| `crewHome()` | A (읽기) | `GET /crews/{id}` 크루 홈 조회 |
| `writeScenario()` | B (쓰기) | 크루 홈 본 뒤 `POST /verifications` 인증 작성 |
| `crewRush()` | D (정원경합) | `POST /crews/{id}/join` 동시 가입 |
| `dupJoin()` | E (중복가입) | 같은 토큰으로 N발 동시 가입 → 1건만 성공해야 |

## 6. config.js — 토큰과 매핑 (요청이 "누구"인지)

```javascript
// k6/lib/config.js
export const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

// tokens.csv 를 한 번만 읽어 모든 VU가 공유 (SharedArray)
export const tokens = new SharedArray('tokens', function () {
    const csv = open('../../tokens.csv');
    return papaparse.parse(csv, { header: true }).data
        .filter(row => row.token && row.token.trim())
        .map(row => row.token.trim());
});

// VU 번호 → 인증 헤더
export function authHeaders(vu) {
    const token = tokens[(vu - 1) % tokens.length];
    return { headers: { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' } };
}
```

- **`tokens.csv`**: 미리 발급해둔 로그인 토큰 목록. VU마다 다른 토큰 = 다른 유저.
- **`SharedArray`**: CSV를 VU마다 다시 안 읽고 메모리에 한 번만 올려 공유 → 메모리 절약.
- `SCALE` (S/M/L/XL/XXL)에 따라 유저·크루 수가 달라지고, 유저↔크루 매핑 헬퍼도 여기 있다.

## 7. 직접 해보기 — 가장 안전한 첫걸음

**로컬에서 smoke.js부터.** (crew-rush는 RDS·EC2·토큰 800개 세팅이 필요해 첫 연습용으론 무겁다.)

### 준비물 체크

```bash
# 1) k6 설치 확인
k6 version          # 없으면: brew install k6

# 2) 백엔드 로컬 기동 (별도 터미널)
cd triagain-back && ./gradlew bootRun     # localhost:8080 떠야 함

# 3) 시드 데이터 + 토큰 (smoke는 GET /crews/{id} 라서 크루 데이터·토큰 필요)
#    → load-test/sql/README.md 와 scripts/generate-tokens.sh 참고
```

### 제일 작게 한 번 (코드 수정 없이 명령으로 부하 조절)

```bash
cd triagain-back/load-test

# VU 2명, 30초 (smoke 기본값)
k6 run --env BASE_URL=http://localhost:8080 --env SCALE=S k6/smoke.js
```

### 터미널 출력 읽는 법

```
http_req_duration..: avg=45ms  p(95)=120ms      ← 응답시간 (p95=상위 95% 지점)
http_req_failed....: 0.00%                       ← 실패율
checks.............: 100.00%  ✓ 60  ✗ 0         ← check 통과/실패 수
iterations.........: 60                          ← 총 반복 횟수
✓ http_req_duration..p(95)<500                   ← threshold 합격(초록 ✓)
```

끝나면 `results/raw/`에 **HTML 리포트**가 생긴다 (report.js가 만듦). 브라우저로 열면 그래프로 보인다.

### 부하를 직접 바꿔보기 (코드 안 건드리고 `--env`로)

```bash
# crew-rush를 VU 20명으로 줄여 로컬 연습 (DB reset 먼저!)
psql "$DB_URL" -f sql/07_rush_reset.sql            # 매 실행 직전 필수
k6 run --env BASE_URL=http://localhost:8080 \
       --env TARGET_VUS=20 --env MAX_MEMBERS=10 \
       k6/crew-rush.js
# → join_success==10, join_full==10 나오면 락이 정상 동작하는 것
```

> ⚠️ **주의**
> - crew-rush 실행 전 **항상 `sql/07_rush_reset.sql`로 정원 리셋**. 안 하면 이미 가입된 상태라 결과 오염.
> - **prod 서버에는 절대 부하 금지** — 로컬/EC2 테스트 서버만.

## 8. 멘탈 모델 (한 장 요약)

```
명령줄:   k6 run --env TARGET_VUS=50 crew-rush.js
            │           │
            │           └─→ __ENV.TARGET_VUS 로 스크립트가 읽음
            ▼
crew-rush.js   = "부하 모양" 정의 (executor·VU 수·threshold)
            │ import
            ▼
scenarios.js   = "행동" 정의 (http.post 로 실제 요청)
            │ import
            ▼
config.js(토큰·URL) + metrics.js(카운터) = 부품
            │
            ▼
report.js      = 성적표(HTML/JSON) 저장
```

기억할 핵심 단어:
**VU**(동시 유저) · **iteration**(반복) · **executor**(VU 굴리는 방식) · **check**(참/거짓 검사) · **threshold**(합격선) · **`--env`**(코드 안 고치고 부하 조절)
