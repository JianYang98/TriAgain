# write-test.md — 테스트 작성/수정 Skill

> **트리거**: 도메인 변경, API 추가/수정, 비즈니스 규칙 변경 후 테스트 작업이 필요할 때
> **이 파일을 읽지 않고 테스트를 작성하는 것은 규칙 위반이다.**

---

## 0. 원칙

- **변경 먼저 분석, 테스트는 그 다음이다.**
- 코드를 수정하기 전에 "이 변경이 어디까지 영향을 주는가"를 먼저 파악한다.
- 깨진 테스트를 고치는 것이 새 테스트를 쓰는 것보다 우선이다.
- 테스트가 없는 영역을 발견하면 반드시 보고한다.

---

## 1. 파급력 분석 (Impact Analysis) — 반드시 먼저 수행

변경 작업을 받으면, 코드를 건드리기 전에 아래 순서로 파급력을 분석한다.

### Step 1: 변경 유형 분류

| 변경 유형 | 예시 | 파급 범위 |
|-----------|------|----------|
| 엔티티 필드 추가/수정 | Crew에 `verificationContent` 추가 | 넓음: Entity → DTO → API → Cucumber 스텝 → E2E |
| 비즈니스 규칙 변경 | Grace Period 로직 수정 | 중간: 도메인 단위테스트 → Cucumber 시나리오 |
| API 엔드포인트 추가 | `PATCH /api/crews/{id}` 신규 | 중간: 새 테스트 필요 + TestAdapter 추가 |
| API 응답 구조 변경 | CrewResponse에 필드 추가 | 넓음: Cucumber assertion → E2E 검증 |
| 내부 리팩토링 | 서비스 메서드 분리 | 좁음: 해당 단위테스트만 |
| 상태 전이 변경 | Challenge 상태 머신 수정 | 넓음: 도메인 테스트 → Cucumber → E2E |

### Step 2: 영향받는 파일 추적

변경된 클래스/파일에서 출발하여 의존 체인을 따라간다.

```
[변경 지점]
  → 이 클래스를 사용하는 서비스는?
    → 이 서비스를 호출하는 컨트롤러는?
      → 이 API를 테스트하는 Cucumber feature는?
        → 이 시나리오를 포함하는 E2E는?
```

**구체적 추적 방법:**
1. 변경된 파일에서 `grep -r "변경된클래스명"` 또는 IDE 참조 검색
2. 영향받는 테스트 파일 목록을 만든다
3. 각 테스트가 어느 레벨인지 분류한다 (단위 / Cucumber / E2E)

### Step 3: 파급력 리포트 작성

분석 결과를 아래 형식으로 정리한 후, 사용자에게 보고한다.
**리포트 승인 전까지 테스트 코드를 수정하지 않는다.**

```
## 파급력 분석 리포트

### 변경 내용
- [무엇을 어떻게 변경했는지]

### 영향받는 테스트

#### 깨질 가능성 높음 🔴
- [ ] 파일명 — 이유

#### 수정 필요 (깨지지는 않지만 업데이트 필요) 🟡
- [ ] 파일명 — 이유

#### 새로 작성 필요 🟢
- [ ] 어떤 테스트를 왜

#### 영향 없음 확인 ⚪
- 확인한 범위: [어디까지 봤는지]

### 테스트 커버리지 빈 곳 (발견 시)
- [테스트가 없는 영역]
```

## 2. 테스트 레벨별 작성 가이드

TriAgain은 3계층 테스트 구조를 따른다. 아래에서 위로 쌓는다.

```
         E2E (해피패스 5개) — ./gradlew e2eTest
      Cucumber BDD (17 feature, 60+ 시나리오) — 한국어 스텝
   단위테스트 (40+ 테스트) — 도메인 모델 + 서비스 + 어댑터
```

---

### 2-1. 단위테스트

**대상**: 도메인 모델, 서비스 로직, 어댑터
**DB**: H2 인메모리
**프레임워크**: JUnit 5 + Mockito + AssertJ

#### 작성 기준

| 이럴 때 단위테스트를 쓴다 | 예시 |
|---------------------------|------|
| 도메인 모델에 비즈니스 규칙이 있을 때 | Challenge 상태 전이, Crew 참여 조건 검증 |
| 서비스 메서드에 분기 로직이 있을 때 | 마감 시간 + Grace Period 판단 |
| 검증 로직이 있을 때 | 닉네임 2~12자, verificationContent 50자 제한 |
| 예외를 던지는 경로가 있을 때 | 이미 참여 중인 크루에 재참여 시도 |

#### 컨벤션

```java
@DisplayName("설명 — 한국어로 '~하면 ~한다' 형식")
@Test
void 메서드명은_영문_snake_case() {
    // given — 준비

    // when — 실행

    // then — 검증 (AssertJ)
    assertThat(result).isEqualTo(expected);
}
```

#### 주의사항
- 서비스 테스트에서 외부 의존성은 Mockito로 모킹한다.
- 도메인 모델 테스트에서는 모킹 없이 순수 로직만 테스트한다.
- `@DisplayName`은 반드시 한국어로 작성한다.

---

### 2-2. Cucumber BDD (인수테스트)

**대상**: API 레벨 비즈니스 시나리오
**DB**: TestContainers (PostgreSQL 16)
**프레임워크**: Cucumber 7.17.0 + REST-Assured 5.5.0
**키워드**: 한국어 (`@기능, @시나리오, @조건, @만일, @그러면`)

#### 작성 기준

| 이럴 때 Cucumber 시나리오를 쓴다 | 예시 |
|----------------------------------|------|
| 사용자 관점의 비즈니스 플로우 | 크루 생성 → 참여 → 인증 → 완료 |
| 에러 케이스가 비즈니스 규칙에서 나올 때 | 마감 후 인증 시도 → 실패 |
| 여러 API가 연결되는 시나리오 | 크루 생성 → 수정 → 삭제 |
| 권한/인증 관련 시나리오 | 크루장만 수정 가능 |

#### Feature 파일 컨벤션

```gherkin
# language: ko

@기능
기능: 크루 수정

  배경:
    조건 테스트 유저 "user1"이 로그인되어 있다
    그리고 "user1"이 크루를 생성했다

  @시나리오
  시나리오: 크루장이 크루 이름을 수정한다
    만일 "user1"이 크루 이름을 "새이름"으로 수정 요청한다
    그러면 응답 코드는 200이다
    그리고 크루 이름이 "새이름"으로 변경되어 있다

  @시나리오
  시나리오: 크루장이 아닌 사용자가 수정을 시도한다
    조건 테스트 유저 "user2"가 로그인되어 있다
    만일 "user2"가 크루 수정을 요청한다
    그러면 응답 코드는 403이다
```

#### 스텝 정의 컨벤션

- `ScenarioContext`를 통해 시나리오 간 상태(crewId, userId, response 등) 공유
- `DatabaseCleanup`이 매 시나리오 전 TRUNCATE 수행 → 스텝 간 독립성 보장
- `TestAdapter` 패턴 사용: HTTP 호출은 직접 하지 않고 `CrewTestAdapter`, `AuthTestAdapter` 등을 통한다
- 인증은 `X-User-Id` 헤더 (dev/test 전용)

#### 새 Feature 추가 시 체크리스트

1. [ ] feature 파일 작성 (`src/test/resources/features/`)
2. [ ] 필요한 스텝 정의 확인 — 기존 스텝 재사용 우선
3. [ ] 새 스텝 필요 시 해당 도메인의 StepDefinition 클래스에 추가
4. [ ] 새 API 호출이 필요하면 TestAdapter에 메서드 추가
5. [ ] `./gradlew test`로 전체 Cucumber 통과 확인

---

### 2-3. E2E 테스트

**대상**: 핵심 해피패스 (현재 5개 시나리오)
**DB**: TestContainers (PostgreSQL 16)
**실행**: `./gradlew e2eTest` (별도 task)

#### 작성 기준

| 이럴 때 E2E를 쓴다 | 예시 |
|--------------------|------|
| 전체 플로우가 끝까지 동작하는지 확인 | 회원가입 → 크루 생성 → 인증 → 사이클 완료 |
| 배포 전 스모크 테스트 용도 | 핵심 5개 시나리오 |

#### 주의사항
- E2E는 해피패스만. 에러 케이스는 Cucumber에서 커버한다.
- E2E 시나리오 수는 최소로 유지한다 (느리므로).
- 새 E2E 추가는 "이 플로우가 깨지면 서비스를 못 쓴다" 수준일 때만.

## 3. 변경 유형별 테스트 작업 순서

### 3-1. 엔티티 필드 추가/수정 시

```
1. 단위테스트: 해당 엔티티의 생성/검증 테스트 수정
2. 단위테스트: 서비스에서 해당 필드 사용하는 로직 테스트 추가/수정
3. Cucumber: 응답 assertion에 새 필드 반영
4. Cucumber: 해당 필드가 비즈니스 규칙이면 시나리오 추가
5. E2E: 기존 해피패스가 깨지는지 확인 (보통 수정 불필요)
```

### 3-2. 새 API 엔드포인트 추가 시

```
1. TestAdapter에 새 API 호출 메서드 추가
2. Cucumber: 새 feature 파일 작성 (해피패스 + 주요 에러 케이스)
3. 단위테스트: 서비스 로직 테스트 (분기/검증이 있으면)
4. E2E: 기존 해피패스에 영향 있으면 수정
```

### 3-3. 비즈니스 규칙 변경 시

```
1. 단위테스트: 도메인 모델의 규칙 테스트 수정 (가장 먼저)
2. 단위테스트: 서비스의 분기 로직 테스트 수정
3. Cucumber: 해당 규칙이 적용되는 모든 시나리오 확인 및 수정
4. Cucumber: 변경된 규칙의 경계값 시나리오 추가
5. E2E: 해피패스에 영향 있으면 수정
```

### 3-4. 상태 전이 변경 시

```
1. 단위테스트: 상태 전이 메서드 테스트 전면 재작성
2. 단위테스트: 잘못된 상태 전이 시 예외 테스트
3. Cucumber: 상태 변경이 포함된 모든 시나리오 확인
4. Cucumber: 새 상태 전이 경로 시나리오 추가
5. E2E: 전체 플로우 재확인 (상태 전이는 E2E 영향 높음)
```

### 3-5. 내부 리팩토링 시

```
1. 기존 테스트 전체 실행 — 깨지는 것 확인
2. 깨진 테스트만 수정 (테스트 로직이 아니라 호출 방식만 바꾼다)
3. 새 테스트 추가 안 함 (동작이 안 바뀌었으므로)
4. 전체 테스트 통과 확인
```

### 3-6. 삭제/캐스케이드/정리(cleanup) 경로 변경 시

```
1. 단위테스트: 삭제 가능 조건(도메인 검증) + 서비스 분기 테스트
2. 통합테스트(필수): TestContainers로 실제 삭제를 실행하고, 삭제된 엔티티를
   참조하는 모든 자식 테이블 행이 0건(또는 SET NULL)임을 count로 assert.
   — mock verify(호출 여부)로 대체 금지. FK 제약이 없어 SQL이 틀려도 단위테스트는 그린이다.
3. Cucumber: 삭제 성공/거부(권한·상태·잔여 멤버) 시나리오
4. E2E: 삭제가 핵심 플로우에 포함되면 확인
```

## 4. 테스트 실행 순서

작업 완료 후 반드시 아래 순서로 실행한다.

```bash
# 1단계: 단위 + Cucumber 전체
./gradlew test

# 2단계: 실패 시 — 실패한 테스트만 확인
./gradlew test --tests "실패한테스트클래스"

# 3단계: 전체 통과 후 E2E
./gradlew e2eTest

# 4단계: 전체 통과 확인
./gradlew test e2eTest
```

**`./gradlew test` 통과 전까지 E2E를 돌리지 않는다.**

## 5. 금지 사항

- ❌ 파급력 분석 없이 테스트 코드부터 수정하지 않는다
- ❌ 파급력 리포트 승인 전에 테스트를 고치지 않는다
- ❌ 깨진 테스트를 삭제하지 않는다 (수정한다)
- ❌ Cucumber 스텝에서 REST-Assured를 직접 호출하지 않는다 (TestAdapter를 쓴다)
- ❌ E2E에 에러 케이스를 추가하지 않는다 (Cucumber에서 커버)
- ❌ `@Disabled`로 실패하는 테스트를 무시하지 않는다
- ❌ 한 번에 여러 테스트 레벨을 동시에 수정하지 않는다 (단위 → Cucumber → E2E 순서)
- ❌ hard-delete/캐스케이드 정리 SQL을 mock verify(호출 여부)로만 검증하지 않는다 — 실DB(TestContainers)로 참조행 0건을 assert한다 (FK 제약 부재로 SQL 오류가 단위테스트에서 안 잡힘)
